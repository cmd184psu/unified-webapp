## Spike findings (SP0, 2026-10-13)
Full notes, fixtures, the opencode stub server and the bwrap template are kept outside the repo in `~/agentflow-spikes/` (`findings-{opencode,bwrap,taskmaster}.md`, `fixtures/*.jsonl`, `stub/`, `sb_ro.sh`). Stories copy what they need into `testdata/`.

- **Runner binary (all):** `which opencode` is a bash shim (`~/.agents/.cache/shims/opencode`) that fails with a replaced HOME. Use the real binary `~/.opencode/bin/opencode` (v1.18.19), resolved before sandboxing and ro-bound into the sandbox. The server env carries `OPENCODE_CONFIG_DIR` (leaks the user's config) — the child env must be an allowlist.
- **S1 prompt delivery — FALLBACK met:** `-f file` truncates at ~50 KB; argv caps at 128 KB. Piping the prompt on **stdin with no message argument** delivered 500 KB (3/3) and 2 MB intact. Always set Stdin explicitly (an open never-closed pipe hangs `opencode run`).
- **S2 permissions — MET:** last-match-wins. Emit `"*": allow`, then `"git *": deny`, then each read-only git subcommand allow; plus `external_directory: deny`. Denies hold with/without `--auto`, catch compound commands, `$()`, `git -C`. `edit: deny` removes edit/write tools but not shell writes. Not caught: `/usr/bin/git`, `env git`, `sh -c` → GIT5 layers 2-3 (read-only gitdir + detect-and-revert, no creds) are required.
- **S3 isolation — MET:** `--pure` + `XDG_CONFIG_HOME=<stage>/xdg` (config at `<stage>/xdg/opencode/opencode.json`) + fresh HOME + scrubbed env + `OPENCODE_DISABLE_PROJECT_CONFIG=1`. Then a marker plugin is not loaded and generated agents are. `OPENCODE_CONFIG` is additive (insufficient alone); `OPENCODE_CONFIG_DIR` must never be passed. Provider keys must come via generated config or `OPENCODE_AUTH_CONTENT` (not tested with real keys).
- **S4 sandbox — MET:** bwrap 0.10.0, userns unrestricted. Read-only git works with `.git` AND `.git/worktrees/<id>` ro-bound; writable set = worktree + stage home only. commit/branch/update-ref/add/stash fail; `~/.ssh` etc. unreadable; no SSH agent. `--clearenv` must precede `--setenv`. Env allowlist: PATH, HOME, LANG, TERM=dumb, GIT_TERMINAL_PROMPT=0, GIT_CONFIG_GLOBAL=/dev/null, GIT_CONFIG_NOSYSTEM=1, GIT_OPTIONAL_LOCKS=0, XDG_*, GOCACHE, GOMODCACHE, GOPATH, GOTOOLCHAIN=local. Go deps: network or ro host GOMODCACHE + GOPROXY=off (0.27 s). **Extra:** the plan's `--ro-bind / /` leaves `/opt/unified-webapp/data/*`, `.git`, source and sibling stage dirs readable → B8 uses a deny-by-default root (ro-bind /usr, /etc, libs; tmpfs /home, /run, /tmp; bind only repo .git ro, worktree, stage home, runner binary) with tests that data dir, sibling stage and config are unreadable (this is within B8's own "no credentials reachable" scope).
- **S5 events — MET:** JSONL on stdout: `step_start`, `text`, `tool_use`, `step_finish`, `error`. Final text = last `text`; usage = sum of `step_finish.part.tokens` (per-step vs cumulative unverified). Errors: one `error` event + exit 1 — 429 (`statusCode` 429 + retry-after) → rate_limit; 500 → crash; no statusCode "Cannot connect" → unreachable; zero events → timeout. opencode retries internally (up to ~76 s) → adapter timeout must be well above 90 s. Rejected `ask` exits 0 with last step_finish reason `tool-calls` and no text → incomplete. SO2 corrective: `--session <id>` with the same HOME/XDG/cwd, new prompt on stdin.
- **S6 taskmaster — MET:** ctx cancel < 10 ms for Cancel, brake and Close. Cancel: queued → canceled; running → canceling → canceled. Pause keeps queued queued, leaves running alone. Brake cancels running jobs and pauses only unpaused lanes; release unpauses only those. Close: running → `failed: context canceled` (treat as infra:lost), queued stays pending. Width 0/-1 rejected by UpdateSettings; `InitialWidth:0` allowed. Pending jobs with unregistered kinds stay pending; RegisterLane after Open works (job starts next poll). Rule: if `BrakeEngaged` do nothing; pause only if not paused; unpause only if `PausedBy=="owner:agentflow"`. Reroute = Cancel + Submit. Second RegisterLane same name → ErrLaneRegistered.

## Owner design notes (2026-10-14, next phase, not fixed)

- **Settings belong in the hamburger menu, not their own tab.** Other modules keep their settings in the shared hamburger drawer; agentflow put them on a Settings tab, which breaks the house design. Move Settings into the hamburger (`web/agentflow/js/main.ts` `initHamburger`, Settings view) and drop the tab.

Known boot-time reads: the `AGENTFLOW_KEY_*` environment keys ("read once at boot", `docs/guides/agentflow.md`), the opencode binary path (inert `opencode_path`), and the opencode version/health check. Audit every key behind `PUT /api/settings` and make each one apply at use time or on a reload hook run by the PUT handler. ## Next phase: automate FRD authoring (planned 2026-10-14, owner-approved direction)

Goal: writing an FRD is not a form-filling exercise. The human describes what they want in plain words and approves; the system does the rest.

- **N1 Definition of done (deterministic).** A project-level definition of done derived from the detected toolchain (Go: builds, vets, tests pass; Python: pytest passes; npm: tests pass; all: no unrelated files changed, new code has tests, no secrets added). Read-only on the FRD tab, attached to every task and to the reviewer prompt, overridable per project. The engine's verify stage already runs the commands, so acceptance criteria no longer restate them. A criterion such as "go test passes" becomes redundant and the drafter must not emit it.
- **N2 Description-only FRD with an AI draft.** The FRD tab opens with one plain-language box ("what do you want?"). A draft stage (planner role, read-only repo view, same sandbox as plan stages) returns a full FRD: title, objective, requirements, acceptance criteria, out of scope. The human reviews it as a document, edits any part, and approves. The existing structured editor stays as the "edit" view of the draft.
- **N3 Deterministic filler.** Ids (R1.., AC1..), the links from criteria to requirements, group assignment, status and dates are generated by code in the API on save, never typed. Validation errors name the field but never ask the user for an id.
- **Automate further:** a project's first FRD can be offered a description seeded from the repo (README, open TODOs); a green check (all requirements covered by a criterion) is computed, not asserted.

Acceptance: from a one-sentence description to an approved FRD takes one review click, with no id or boilerplate criterion typed; the drafted FRD never contains an AC that restates the definition of done; a unit test per story; UI follows the owner rules above (toggles, shared components, symbols, no typing where a list can be offered).

The items are attached to the worker and reviewer prompts ("## Definition of done") and shown read-only on the FRD tab. Drafted criteria must not restate them.
2. `POST /api/projects/{slug}/efforts/{id}/frd/draft` body `{"description": str, "polish": bool}` -> 202. Runs a planner-role stage that returns an FRD (polish = tidy the existing FRD instead of drafting from the description); the result is saved as a new unapproved FRD revision and `effort.update` fires. `GET .../frd/draft` -> `{"state": "idle"|"running"|"failed", "started": ms, "error": str}`.
3. Deterministic filler on every FRD save (PUT frd and the draft result): ids R1../AC1.. assigned when empty, an acceptance criterion with no requirement links covers all requirements, default group, status `draft`, created date. A FRD with no ids typed is valid.
4. `GET .../efforts/{id}/size` -> `{"frd_tokens", "plan_tokens", "budget_tokens", "context_tokens_min", "over": bool, "models": [{"backend","model","context_tokens"}], "advice": str}`. Tokens are estimated (chars/4). `budget` = half of the smallest context among the candidates for the planning roles; 0 context = unknown, then no `over`.
5. `POST .../frd/split` body `{"max_parts": int?}` -> 202 (planner-role stage returning `{"parts": [FRD..]}`); on success part 1 becomes the effort's FRD (new revision) and parts 2..N are stored. `GET .../frd/parts` -> `[{"n","title","summary","tokens"}]`; `POST .../frd/parts/{n}/start` creates a new effort from part n (409 while the project has an active effort).
6. Backend models gain `context_tokens` (int, 0 unknown) on create/patch/view; the host probe returns the existing `models: [str]` plus `contexts: {name: tokens}` (Ollama `/api/show` model_info `*.context_length`, best effort).
