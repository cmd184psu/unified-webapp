# Phase H: harden agentflow against weak models (planned 2026-10-15)

Source: the two webcalc trials on the live service (efforts 3 and 4, same one-sentence spec, same engine).

| | Free models (effort 3) | Local models (effort 4) |
|---|---|---|
| Result | works, matches the spec | marked complete, does not work |
| Port | 7070 | 8080 (spec said 7070) |
| Routes | `/api/add` … `/api/history` | `/arithmetic/add`, `/history` |
| `GET /` | page | 404 |
| Time, stages, tokens | 16 min, 20, 0.55M | 148 min, 48, 6.0M |

The engine's gates (build, vet, tests, reviewer) all passed on the broken build. The unit tests were written by the same weak model that wrote the code, so they agree with it.

## Findings

1. **The port was lost at the first step.** The owner's sentence says port 7070. The local FRD draft (qwen3.6) has no requirement mentioning it (0 occurrences in FRD and plan). The planner then invented 8080. The free-model FRD kept it. Nothing in the engine notices that a stated fact vanished.
2. **The compiler compresses literals away.** The plan for effort 4 still had `POST /api/add` and friends. The compiled task prompts say "mapping POST endpoints for add subtract multiply divide", and the criteria are paraphrases ("Arithmetic endpoints return HTTP 200"). `compiler.md` rule 3 asks for "two to five short sentences", which squeezes out exact strings. Acceptance criteria are not required to quote anything.
3. **The reviewer cannot catch what the criteria do not say.** qwen3-coder approved the wrong routes and the wrong port because the criteria it was given do not contain them.
4. **Reviewer independence is partial.** `skipReviewer` (engine/dispatch.go) only rejects a reviewer whose model name equals the worker's. Same-family models (two qwens) still review each other.
5. **No model classes.** A candidate list is just an ordered list per role. A weak local model can land on planner or reviewer, and nothing says a reviewer should be at least as strong as the worker.

## Decisions (defaults; change before building if wrong)

- **Independence is soft, then loud.** Prefer a reviewer from a different family than the worker; if none is eligible, accept a different model of the same family; if none, wait as today. The attempt records which level was used and the UI shows it on the task. Not a hard block, because with only local models a hard family rule could stall a run.
- **Tiers are owner-set, with evidence on its own tab.** Each backend model has a tier: 1 strong, 2 capable, 3 light. A role has a floor. Per-model results from past runs (stages, repairs, infra failures, time and tokens per stage) get their own top-level **Stats** tab beside Overview, Project and Backends (owner, 2026-10-15: it must be handy, not buried low on a nearly unrelated page). No automatic reassignment.
- **Role floors:** drafter, planner, architect, critic, compiler: tier 1 or 2. Reviewer: its tier must be at or better than the worker's tier for that attempt. Worker: any tier. A candidate under the floor is skipped with a stated reason, exactly like the paid and hosted rules.
- **Family** is derived from the model name (`qwen*`, `mistral*`, `llama*`, `gpt-oss*`, `deepseek*`, …) and can be overridden per model; unknown names are their own family.

## Stories

**H1 Literal-facts guard.** (root cause for findings 1 to 3)
- Engine extracts literals from the owner's description deterministically: ports (`port N`, `:N`), URL paths, HTTP status codes, backticked and quoted strings, JSON field names in braces, file names. Stored with the effort.
- After the FRD draft: every literal must appear in the FRD text. A miss gets one corrective follow-up with the missing list named, then the draft fails visibly. Same check on the approved plan and on the compiled queue (each literal must appear in at least one task prompt or criterion).
- Prompt changes: drafter, planner and compiler copy literals verbatim; compiler rule 3 loosened so a prompt may be longer when it carries literals; each interface criterion must quote its literal (`POST /api/divide` with `b=0` returns 400 `{"error":"division by zero"}`).
- Reviewer prompt carries the FRD requirement text for the task's criteria, verbatim.
- Tests: a draft dropping the port fails then repairs; a compiled queue dropping a path is rejected.

**H2 Reviewer independence.** `family` on backend models (probe fills it, override in the UI); `reviewerFor` prefers a different family, then a different model; the attempt records the level; the task row shows it; tests for each of the three outcomes and for the sticky reviewer.

**H3 Model tiers.** `tier` on backend models (migration), role floors in the dispatcher with stated skip reasons, reviewer-not-weaker-than-worker rule, tier control on the Backends model rows, docs.

**H6 Install a model from the UI.** (owner, 2026-10-15) On the Backends page: pick an Ollama backend, name a model, press Install. The service calls the host's `POST /api/pull` (no ssh needed; it is the same API I used by hand on 2026-10-15 for devstral-small-2 and gemma3:27b), streams the progress (layer, bytes done of total) to a progress bar through a job record in SQLite so a page reload or service restart still shows it, and on success adds the model to the backend with a tier chosen at install time. **H7 Repeat failures change the model; three strikes bench it.** (owner, 2026-10-15, after effort 5 stalled on T003: qwen3.6:35b wrote a result file with one stray backtick three attempts running, and the task was declared stuck with other models idle.) The strict check stays strict; nothing tolerates junk.
- A model that has failed a task's latest attempts the same way (same fingerprint, same worker) from `stuck_threshold - 1` of them is passed over for the next attempt; if no other model could ever serve, the repeat runs so the task still reaches stuck.
- A strike is derived from the stages and attempts tables: unparseable output, a git policy violation, or the repeat above. Strikes are a streak (owner, 2026-10-15: like failed password attempts): a success by the model in that role resets the count to zero, and three in a row bench it, whether local, free or paid; the dispatcher skips it with the reason. The history is never deleted (owner: keep failures and metrics to track over time): `GET /api/strikes` returns every strike with kind, where, when and whether it still counts, plus per-day counts, and the Stats tab shows it with the streak, the lifetime total, a benched badge and a Clear button. Migration 13 stores only when the owner last cleared.

**H8 An unreachable backend is suspended, not retried, and blames nobody.** (owner, 2026-10-15, after switching off the m5.) A stage that ends `infra:unreachable` suspends its backend until a plain HTTP check of its address answers (checked on the reconcile tick); no task infra-retry strike, no backoff, no halt, no model strike. Backends without an address keep the timed cooldown. Repeat strikes count only verify and review fingerprints, so timeouts and merge conflicts are not held against a model.

**H9 A plan for merge conflicts (to come back to).** (owner, 2026-10-15: avoiding them is best, but some cannot be helped, so there must be a plan.) Today a conflict ends the merge stage `repair` and the next worker in the list gets an ordinary repair attempt, with no say over which model, and a weak model may keep one side, drop the other, or leave markers. Proposed, cheapest first:
1. **Prevention.** Reject or flag an attempt whose diff touches files outside the task's `files_touched`, and serialize tasks that share a file. (T003 of the 2026-10-15 webcalc run conflicted in `main_test.go`, which belonged to T002 running beside it.)
2. **A deterministic ladder** (owner, 2026-10-15: deterministic code first, an agent only for what is left). Tried in order on a conflicted merge, each rung followed by the normal verify (build, vet, tests) before it is accepted, because a clean merge is not a correct one:
   - a better textual merge: git's patience or histogram diff;
   - formatting-only differences: `gofmt`, then merge again;
   - union (keep both sides) for files where both sides only added independent things at the same spot: appended test functions, imports, route registrations, list entries, docs. A duplicate definition or a failing build after a union hands the conflict to the next rung instead of being accepted;
   - generated or derived files are regenerated, not merged (`go.sum` by `go mod tidy`);
   - a structure-aware merge (Mergiraf-style, by syntax tree) if one that supports the project's language is installed; check Go support before relying on it.
3. **An agent for what is left.** A `resolver` role with its own candidate list and a floor of tier 1 or 2 (never tier 3). Its prompt carries both tasks' prompts and acceptance criteria, the conflicting files with both sides, and the instruction to keep both intents; it works in the task worktree after the integration branch is merged into it, so the resolution is an ordinary commit that goes through verify and review again.
4. **Escalate, don't loop.** A conflict that survives one resolver attempt goes to the next tier up, and then halts for the owner with the two diffs shown, never silently retried. A conflict is never a strike against the worker that caused it; a resolver gets strikes like any model if it leaves markers or an unreadable result.
5. **Evidence.** Record which rung resolved each conflict (and for the agent, which model), and show conflicts per task, per file and per rung on the Stats tab, so it is measured how much the deterministic rungs absorb and whether the agent is needed often.

**H10 What stalled in effort 6 (2026-10-16) and the mitigations.**
- *The overnight stall was a gate, not compute.* Planning ran 45 minutes (22:54 to 23:37; the critic's two rounds on the m4 took 33 of them) and then waited at plan approval for 13.5 hours, because the external kickoff script gave up after 30 minutes and nothing else approves gates. Fixed in the script (6-hour waits, `--resume`). Still open: (a) an unattended trial should use the engine's own YOLO mode instead of an external poller; (b) a gate that has waited a long time should show how long on the project card; (c) order candidates within a tier by observed speed (Stats data), so a slow host is not the default critic.
- *A model that cannot do tool calls was listed.* `gemma3:27b` answers `does not support tools`; the runner needs tools. Five instant crashes burned T003's whole infrastructure budget in three minutes, and T003 (needs attention) blocked T004 and T006. To build: (a) read the host's reported capabilities (`/api/show` lists `tools`) when a model is probed or installed, store them, and skip a model without `tools` for every runner role with a stated reason; (b) a deterministic refusal (`does not support tools`, unknown model) is permanent, not transient: take the model out at once instead of retrying it, and spend nothing from the task's budget; (c) an infra retry should avoid the model that just crashed, not only the backend.
- *The server is not the bottleneck.* The service itself idles (0.1% CPU); load average 18 comes from the VM guests and one OMC rate-limit daemon; verify stages take about 0.1 minutes.

**H15 Context windows (owner, 2026-10-17; H15a to H15c built, H15d not).** Effort 8 (`webcalc-t2`) stalled on T001: devstral's worker was cut off at exactly 16384 tokens (`finish reason length`) and the engine charged the cut-off to the model as an unparseable reply. The window Ollama served (16384) was far below what the model supports (devstral 393216), and agentflow knew only the second number. Owner's direction: know each model's window, calculate in Go whether a task fits before it runs, send a task that is too big for the window back to planning, assume a floor, and extend the window as far as the host allows.

- *H15a, windows.* `backend_models` has `window_tokens` and `window_source` (`set`, `observed`, `host`) beside `context_tokens`, which is now only the model's maximum from `/api/show`. `engine.Window(model, floor)` gives the window the engine assumes: the served window when known, otherwise the `context_floor_tokens` setting (default 16384, in Settings), never more than the model supports. A run cut off by a full window ends `infra:context_full` and records the size at the cut-off as the model's window (`observed`; the owner's own value is never replaced, and a learned one only moves down). The Backends form's window field is the served window; the host's maximum is no longer put into it. A save that leaves it blank keeps what the server learned.
- *H15b, size in advance.* `engine.TaskNeed(promptTokens, files)`: (prompt + 2 x the files' size + 2000) x 1.1. Calibrated on the first local trial: a three-file task peaked at 7.9K on its first attempt (a 4.6K prompt, of which about 3.8K is the agent's own overhead and the run-time sections), and its repair attempts, which carry the previous diff, started at 7.5K to 9.7K and were cut off at 16K. A file counts 1500 tokens, a page file (html, css, js) 2500. The constants are in `engine/context.go`; the real windows are learned, so a wrong guess costs a reroute.
- *H15c, back to planning.* At compile time a task whose need exceeds the largest window among the project's usable worker candidates makes the queue invalid; the compiler gets one more try whose prompt names the task, the numbers and "split it" (rule 15 in `compiler.md` asks for one source file and its test, or one page file, per task), then the compile halts. At dispatch a worker candidate whose window is smaller than the task needs is passed over; if none is large enough the task runs in list order instead of waiting. A task cut off on every model is not yet sent back to the compiler automatically (the queue is fixed once approved); it halts as an infrastructure failure naming the window.
- *H15d, extend the window (built, not yet used on a live host).* Each Ollama backend has a memory budget (`memory_budget_mb`: what one loaded model may use, weights plus context cache) and an optional window cap (`window_cap_tokens`). `POST /api/backends/{name}/extend-windows` (`{"apply": false}` only reports) works out, per model, the largest window that fits: (budget - weights from `/api/tags` - a margin of 5%, at least 1 GiB) divided by the cache cost per token from `/api/show` (layers x kv heads x (key + value size) x 2 bytes at f16; layers that keep no cache, per `full_attention_interval`, are left out; an architecture that does not say gets a conservative guess), capped by the model's maximum and the backend's cap, in steps of 1024, and applied only if it reaches the floor. It re-creates the model under its own name with that `num_ctx` (`/api/create`, `from` = itself; the weights are shared) and records the window with source `host`. The worker prompt allows the smallest fix in a finished task's file when its own tests expose a defect, to be named in `summary`; the reviewer prompt treats an unexplained out-of-scope file as a major issue. The scope failure text now says the file belongs to an unfinished task, to leave it alone, and to report `blocked` naming the file if the task cannot be done without it.
- **Compile.** A tests-only task whose test files sit in the directory of code that earlier tasks in its chain write is sent back to the compiler (`QueueTestShapeProblems`), with the same two retries as the other queue checks. Compiler rule 10 already said to put code and tests in the same task; the model ignored it, so the engine now checks. Tests across directories (end to end) are allowed.
- The probe of that run (build 3/3, API 68/106, page 5/5) shows what the late tests were for: the evaluator, input validation, history and some domain errors were wrong.

**H18: the owner is told when work stops on its own.** `GET /api/attention` lists what has halted and waits for a person: an FRD draft that failed, a plan or compile that halted, a task that is exhausted, stuck or needs input, a task no model can take ("no eligible backend"). It is derived from the audit log and task state, so it is right after a restart and clears when the owner acts. The UI shows a banner above the tabs with a link per project, the count in the browser tab title, a toast for an item that appears while the page is open, and a desktop notification if the browser already allows them. Found when a halted planning gate sat for eight hours, and again when a task waited three hours for a reviewer no rule allowed. Not covered: a task that is merely slow, and notification when no page is open (a webhook or mail would be next).

**H16d: a crash or timeout does not use up a try, and its retry avoids every model tried.** The third local trial halted at compile after eight hours of no news: devstral's queue left out the request's strings, qwen3.8:27b then timed out after its 30 minutes, and the timeout counted as the second of three tries while its retry avoided only qwen3.8, so devstral got the last try and failed the same way. The tries for a wrong reply (draft: four, compile: three) now count only replies that were read, and a retry after a crash or timeout in a draft or compile avoids every model already tried in the run. The halt was found by the new `/api/attention` banner; the kickoff script now also stops as soon as the service lists an item for its effort, instead of waiting out its six hours.

### H19 A task is held to the requirements it names

Effort 13 (local trial) exhausted T001 ("basic web server with HTML page") in five attempts. The FRD, drafted by a small model, linked every acceptance criterion to every requirement R1 to R9. `frdSection` expands a cited criterion into its linked requirements, so the T001 worker and reviewer both received the whole FRD. The worker wrote the whole application in one 849-line file and the reviewer then demanded R3, R4 and R7 of a task that owns only the page; the repairs corrupted the file. `frdSection` now uses the requirements a task names itself and follows a criterion's links only when the task names none. Test: `TestH19_TaskNamingARequirementIsNotGivenEveryLinkedRequirement`.

### H20 Duty cap per backend

A host that runs hot (the M5 power brick) can be held to a lower pace without taking it offline. Each backend has `duty_percent` (10 to 100; 100 is no cap, stored as 0), set by `PATCH /api/backends/{name}` and by the Pace choice on the backend card, applied at once with no restart. After a stage ends the backend is given no new one for the stage's running time times (100-d)/d, up to 30 minutes (`BackendRestUntil`); stages already running are not touched, and a task that waits says "backend X is resting under its duty cap until HH:MM". Disable (retire) remains the way to stop a host now. The cap is part of the configuration export.

### H21 A worker timeout sends the task to another model at once

Effort 14 T007 used its five attempts after M5 was taken offline: four were 30-minute worker timeouts on the same win model. `repeatFailers` passed a model over immediately only after a blocked or unreadable result; a timeout needed two in a row, and an attempt on another model in between reset the count, so the slow model got the task back. A worker timeout now counts like the other two. When no other model could ever serve, the model is still used again (the existing fallback). Test: `TestH21_AfterAWorkerTimeoutTheNextAttemptUsesAnotherModel`.

### H22 A file list that disagrees with the path in the prompt goes back to the compiler

Effort 14 T006 stopped for input because `files_touched` said `history.store.go` while the prompt, the worker and the repository used `history/store.go`; the reviewer was told to read a file that does not exist. `QueueFileNameProblems` flags a listed name that is a prompt path with its slashes turned into a dot, underscore or hyphen, and the compile retry sends the compiler back with the finding. Test: `TestQueueFileNameProblemsCatchesASlashTurnedIntoADot`.

### H23 A compile retry is given the queue it must fix

Effort 15 halted at compile after three queues, each missing different strings (`count`, 400, 405, `7 + 2`): the retry prompt said "fix these in the queue you wrote before" but did not show the queue, and did not list the missing strings, so each model wrote a new queue from scratch. The retry prompt now lists the missing strings and the other findings, and includes the earlier queue with the instruction to keep what is right and change only what the findings say. Covered in `TestQueueProblemRetryUsesAnotherModelAndAThirdTry`.

### H24 Sampling temperature and the Ollama host settings

The generated opencode config set no sampling parameters, so every model ran at its server's default (Ollama: temperature 0.8, top_p 0.9). Each agent now carries `temperature` (0.2; 0.4 for the planner and architect, whose revisions should be able to differ) and `top_p` 0.9, which the OpenAI-compatible endpoint Ollama exposes honors. Ollama's own options that this endpoint cannot carry (`num_ctx`, `top_k`, `repeat_penalty`) stay a host or Modelfile matter. The hosts were read, not changed: M5 and M4 run Ollama from a launchd file (`~/Library/LaunchAgents/com.ollama.serve.plist`) with flash attention on, `OLLAMA_KV_CACHE_TYPE=q8_0` and `OLLAMA_CONTEXT_LENGTH=16384` (M5 also `OLLAMA_KEEP_ALIVE=15m`, `OLLAMA_MAX_LOADED_MODELS=1`); win has the same set as environment variables with flash attention off; builder's systemd unit sets none. The trial kickoff gained `--lineup hybrid` (free hosted models plan, compile and review; local models work).

### H25 Restart the service from the API

So that the service can be restarted without the owner at a terminal (and without sudo), `POST /api/service/restart` (body `{"cancel_running": false, "resume": true}`) pauses every running project, waits until no stage is open, records the paused projects in the audit log (`service.restart`) and ends the process with SIGTERM; the unit's `Restart=always` starts it again on whatever binary is on disk, and on boot the paused projects are started again (`service.restarted`). `cancel_running` stops the projects instead, which cancels their stages. `GET` reports the state and the number of open stages; `DELETE` abandons a pending restart and starts the projects it paused. Nothing is cut short unless `cancel_running` is set; the wait is bounded at an hour. The Settings drawer has a Service section with the button. Tests: `TestH25_RestartWaitsForOpenStagesThenEndsTheProcess`, `TestH25_ResumeAfterRestartAnswersTheRequestOnce`, and the API walk.

### H26 A halted plan is reported, and a crash moves on

Planning that gave up after five infrastructure failures put the effort back at draft, where the attention list did not look, so the trial sat idle for hours with nobody told. A halted plan is now listed whatever the effort's status. A crashed planning stage also avoids every model of that role that already crashed, as the compile and draft retries do, so two flaky models cannot trade the stage back and forth while a third is never asked.

### H27 Check models

The free hosted pool had changed under us: three of five models (space-bunny, cat-jam, muse-spark) answered nothing, not even a one-word prompt, with an instant "Unexpected server error", while the other two worked. Free tiers also run out of quota. `POST /api/backends/{name}/check` (and a Check models button on each backend card) sends a one-word prompt to each model of the backend, one after the other, through the same runner and config a stage uses, and keeps the result per model (`model_checks`, migration 20): answered, not answering, out of quota, unreachable, too slow or an empty reply. `GET` on the same path reports progress. A model whose last check failed is passed over by every picker, with the reason, for six hours or until a later check passes. Infrastructure crashes are still not strikes against a model; this is separate, and owner-triggered.

### H28 A weaker reviewer reviews rather than the task waiting

A reviewer must not be weaker than the worker it judges, but when the pool has none that is not weaker the task waited for ever (T003 of the first hybrid trial waited ten hours for a tier-1 worker's reviewer when only tier-2 hosted models existed). The strict rule still picks first; if every candidate fails only on strength, a weaker one reviews. The worker's own model is never used.

### H29 Local models rank below hosted ones; preflight

The hardware behind a local model is weaker than a datacenter's, so tiers now say so: an unrated model counts as tier 2 if hosted and tier 3 if local, and a local model never counts as stronger than tier 2 whatever its rating. Only a rating the owner set bars a model from planning roles, so a local-only setup still has a planner. `GET /api/projects/{slug}/preflight` looks at a project's candidates the way the pickers will and names any role with no model that can serve it and any worker that would have no reviewer, and warns of hosted models that have not passed Check models lately. The webcalc kickoff script runs Check models and the preflight first and refuses to start on a problem (`--skip-preflight` to skip).

### H30 Stall watchdog

`stall_minutes` (whole minutes, 1 to 100, default 10; a global setting a project may override) defines a stall in two ways. A stage whose model says nothing for that long ends as a timeout, so the usual rules move the work to another model; a model that keeps streaming output is never stalled however long it takes. A running effort, or one being planned or compiled, with nothing in flight and nothing happening for that long is stalled: it is nudged (the planning and dispatch passes run again), recorded once as a `stall.detected` event naming what each task waits for, and listed on the attention list as `stalled`. An effort waiting on a person, in an infrastructure backoff, resting under a duty cap or with every remaining task halted is not stalled.

### H31 Acceptance check of the finished effort

Each task is reviewed alone, so a requirement that cuts across tasks can pass every review and still fail the whole. The first hybrid trial (effort 16) passed all ten tasks and then failed four probe checks: the page did its arithmetic outside the API (R1), `0^-1` gave an empty 200 (R5), `2 3` read as 23 (R6) and a fractional primes count gave the wrong error (R4). When the last task has passed, a reviewer-role stage now reads the merged result in the integration worktree against the approved FRD, requirement by requirement, and answers `pass` or a list of gaps (requirement id, evidence, problem, fix, files; at most six). Each gap becomes a follow-up task `A<round>-<n>` in the same queue (phase `acceptance`, one after another so fixes never edit the same file in parallel, the criterion names the requirement so the worker and reviewer are shown its exact FRD wording), which goes through worker, verify and review as any task does; when they pass, the check runs again. `acceptance_rounds` (0 to 5, default 2, global with a project override) bounds the rounds, so the check runs at most rounds + 1 times. It can never keep an effort from completing: a check that cannot run (infrastructure strikes exhausted, unreadable reply) is recorded as `acceptance.skipped`, and gaps left after the last round are recorded as `acceptance.gaps_left` and an effort warning, and the effort completes. Follow-up tasks are added without changing the approved queue hash (`Store.AddTasks`), so stages in flight are not made stale. Tests: `TestH31_*` in `engine/acceptance_test.go`.

### H32 Check reviewers: seeded-defect cases

A model's one-word check says it answers, not that it reviews. `POST /api/backends/{name}/evals` (body optional: `models`, `layers`, `cases`, `repeats`; 202, runs in the background; `GET` gives progress, a score per model and layer, and every run) shows each model of a backend a small project twice, once with a planted defect and once fixed, in two layers: the per-task review (the real reviewer prompt, with the task, the requirement wording, a passing verify report and the files) and the acceptance check of H31 (the prompt only; the model reads the files itself). The four cases are the four defects the first hybrid trial let through (a page that does its own arithmetic, a power that is not finite answered with 200, `2 3` read as 23, a fractional primes count with the wrong error); each has a second requirement that is met, to catch an invented gap. Per run the outcome is caught or missed (defect), clean or false_alarm (fixed), or unparseable / failed when no verdict was read; the first reply counts, with no corrective follow-up, so a model that needs one scores unread. Results are stored in `reviewer_evals` (the last run of each model and layer) and shown as badges on the Backends tab (button "Check reviewers", default both layers) with the per-case detail in the tooltip. `TestH32_EvalCasesBuildAndTheDefectIsReal` builds every variant and runs a probe test on it, so a case that does not misbehave, or a fix that does not fix, fails the suite. The scores are evidence for tier ratings and for choosing reviewers; nothing reads them automatically yet.
