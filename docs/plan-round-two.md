# Implementation Plan — Round Two: platform auth, passkeys, and binary-wide origin control

**Date:** 2026-09-10
**Status:** v12 (round two, **consensus iteration 4**) — **pending consensus review**.

**Changelog since v11** (v11 was reviewed independently by an Architect and a Critic; both saw the same v11 snapshot, neither saw the other, and **both independently found the same two blocking defects**):

1. **The login rate limiter now has a write path (CRIT-1 — found by both reviewers).** v11's 3.9 specified the limiter's *read* (`Gate.Wrap` step 2a is a pre-request check) and **never specified how a failed login gets recorded**. The failure/success signal is a post-request fact known only inside `handleAuthLogin`, which 3.1 forbade modifying. As written the counter **never incremented**, 3.8's first test was unwritable, and R17 was falsely marked mitigated. **3.1's exception list goes from two to three**: `handleAuthLogin` gains exactly two lines (`RecordFailure`/`RecordSuccess`), the key is computed **once** in step 2a and carried in the request context, and **which outcomes count is now stated explicitly** (credential rejection only — not 400s, not dial errors). `FromConfig` now returns **four** values; 4.9's "three values" text is reconciled. §2A, §3/R17, §7 and 3.8 updated.
2. **`OriginChecker` gains a `RejectFormat` field (CRIT-2 — found by both reviewers).** v11 gave it a single `Logf` field, which **cannot reproduce both existing audit formats** — `sshproxy/proxy.go:315` emits `ws upgrade rejected …` and `broadcast.go:399` emits `broadcast ws upgrade rejected …`. They are *different literal format strings*, not merely different sinks, so A.1's "byte-identical" criterion was unmeetable and **neither existing test would have caught the collapse**. All three format strings are now named (sshproxy, broadcast, and A.2's distinct `cross-origin rejected …`, which is what 6.2's grep recipes were already searching for and would never have matched). `internal/multissh/audit_test.go`'s assertion is **strengthened to the full line** so a future collapse is caught. The accept path must not log.
3. **nginx must set `X-Forwarded-For`, and the limiter's armed state is now visible at boot** (Architect C4). A bare `proxy_pass` does **not** set the header at all, so on a default deployment the limiter would silently never limit, forever, with no signal. 6.2 now mandates `proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;` and states the **trusted-hops-must-append** invariant (without which the rightmost entry is attacker-controlled and the whole trusted-CIDR design collapses). 4.9's boot summary now reports `login-limit=armed(trusted_cidrs=N)`; 6.4 asserts it.
4. **The limiter's map cap is no longer presented as a clean mitigation** (Architect C5). "Drop the oldest on overflow" was itself a bypass — an attacker with >1024 keys evicts their own lockout. Eviction is now "oldest **not currently locked out**; if all are locked out, refuse to track new keys". Recorded as an accepted scale limitation in §4.
5. **The limiter covers all three unauthenticated `/api/auth/*` endpoints** (Architect C6), not just `POST /api/auth/login` — `passkeys/login/begin` and `passkeys/login/finish` are equally unauthenticated credential-verification surfaces, and `begin` additionally grows an unbounded challenge map.
6. **4.11's principal capture is re-specified** (Critic M1). v11's *primary* mechanism was impossible for `/api/ssh/ws`: that route's upgrade handler **is** `package sshproxy`, so "call `auth.PrincipalFromContext` in `internal/multissh`'s own HTTP layer" would have required `sshproxy` to import `internal/platform/auth` — exactly what 4.11 forbids. The `middleware.PrincipalFromRequest` shim is now the **only** mechanism, not a fallback. Also: the principal must **never** be stored on `ConnectParams`, which is populated from the client's post-upgrade message and is therefore attacker-controlled.
7. **The 429 trigger point is now stated one way** (Critic M4). v11 said it three inconsistent ways across 3.9, 3.8/§2A and 6.4 — including a self-contradictory "eleven failed logins… the eleventh returns 429" (a request that 429s never reaches a bind, so it cannot itself be a failed login).
8. **Medium/Minor:** `FromConfig` now **errors** on an unrecognized mode rather than silently returning `NoAuth{}` (C8), with a 3.8 test against `FromConfig` directly; `auth.mode: ""` is normalized to `"none"` **before** B.3's fail-open checks fire (Critic Minor); `PasskeyStorePath` added to B.2's exhaustiveness accounting (C7) and to B.3's validation; `trusted_proxy_cidrs`' default added to B.2; a fourth pre-mortem scenario for the inert limiter (C9); §6A's sweep-term list extended; §6's iteration count and E′ trigger status re-stated honestly.

## 0A. The LDAPS trust correction (new fact, not available when v8 was written)

**The fact.** The operator has verified that `ldaps://ldap.cmdhome.net` is reachable from this machine and that its TLS certificate chains to a root already present in the system trust store. Standard `crypto/tls` verification against the system root CA pool succeeds. There is no custom CA to pin, no `InsecureSkipVerify` to set, and no out-of-band cert-fetching or bootstrap step.

**What v8 assumed instead, located precisely.** v8 said "port `internal/auth` verbatim" and never discussed TLS trust at all — so the assumption is inherited silently from the reference, in two places:

- `reference/multissh/internal/auth/ldap.go:91` dials with `ldapv3.DialWithTLSConfig(&tls.Config{InsecureSkipVerify: c.cfg.InsecureTLS})`, and `:96` does the same for `StartTLS`. Correct code — the posture is entirely determined by the config value.
- `reference/multissh/internal/config/config.go:193-197` — `applyAuthDefaults` sets `LDAP.URL = "ldap://10.100.0.9"`, **`LDAP.StartTLS = true`**, **`LDAP.InsecureTLS = true`**. That is the "unverified until we sort out certs" default, hard-coded, against a plaintext `ldap://` IP literal. A cert cannot be verified against an IP with no SAN, which is presumably why it was set.

v8's task 1.2 already said **do not port `applyAuthDefaults`** — but it gave only one reason (it bakes private lab values into every operator's `WriteDefault` output). The `InsecureTLS = true` half was never named, so an executor porting "the auth defaults, minus the lab hostnames" would have carried the insecure flag across. **This plan names it as the second and more important reason.**

**The corrected design.**

- `ldaps://` with **standard verification against the system trust store** is the default and the documented deployment. `insecure_tls` defaults to **`false`**; `start_tls` defaults to **`false`** (irrelevant for `ldaps://`, and `ldap.go:95` already skips StartTLS when the URL is `ldaps://`).
- **The override knob already exists — it is not invented here.** `insecure_tls` is a field of the reference's own `LDAPConfig` (`ldap.go:19`, `config.go:67`) and is carried across by the field-for-field port in task 1.1. It is retained **for exotic deployments only** and is documented as such. **No `ca_cert_path` / custom CA pool field is added** — there is nothing to point it at, and adding a knob to solve a problem that does not exist is how the insecure default got there in the first place.
- `insecure_tls: true` **logs a `WARN` at `config.Load`** naming the URL and the fact that certificate verification is disabled. It is not rejected — the knob has to work for the case it exists for — but it can never again be the quiet default.
- **`ServerName`: resolved for the `ldaps://` path — and the StartTLS path is a *different* answer.** This distinction is new in v11 and it was the largest defect in v10.

  **On the `ldaps://` dial path, no `ServerName` is needed.** `go-ldap` does not set it and does not need to: `conn.go:191` reaches `crypto/tls` via `tls.DialWithDialer`, which **derives the verification hostname from the dial address** whenever the cloned `tls.Config` leaves `ServerName` empty. So `DialURL("ldaps://ldap.cmdhome.net", DialWithTLSConfig(&tls.Config{InsecureSkipVerify: false}))` (`reference/.../ldap.go:91`) already verifies against that hostname with **zero code change**. **No test may assert that go-ldap sets `ServerName` on this path** — go-ldap leaves it empty by design, so such a test fails against correct, secure behavior and invites someone to "fix" it by hardcoding a name. The regression guard here is one assertion: the `tls.Config` handed to the dial has **`InsecureSkipVerify == false`** under a default config. That, and only that, is what 3.8 pins.

  **On the StartTLS path the derivation does not happen, and v10 was wrong to imply it did.** `conn.go:386` calls `tls.Client(l.conn, config)` — a **different `crypto/tls` entry point**, one that takes an already-established net.Conn and therefore has no dial address to derive from. `reference/.../ldap.go:96` calls `conn.StartTLS(&tls.Config{InsecureSkipVerify: c.cfg.InsecureTLS})` with an empty `ServerName`. With `insecure_tls: false` this is a **guaranteed handshake failure**: `crypto/tls` returns `"either ServerName or InsecureSkipVerify must be specified in the tls.Config"` before a single byte goes on the wire. v10 stated the derivation claim unconditionally in §0A, R13 and 6.2, **forbade** setting `ServerName` in 3.1d, and sent the operator down a debugging path in 6.2 that explicitly told them to stop before reaching the one real fix.

  **The resolution, chosen between the two options the Architect offered: reject the combination at load.** `config.Load` **errors** on `start_tls: true` together with `insecure_tls: false` (B.3), naming the limitation in the message. Rationale: the deployment is `ldaps://` (where `start_tls` is ignored outright — `ldap.go:95` skips it); the only configuration that would exercise a StartTLS `ServerName` is a `ldap://` URL against a host this lab does not have; and adding a `ServerName`-setting branch to the ported dial path means editing reference code for a path nobody runs, which is exactly the kind of speculative knob §0A exists to refuse. **A load-time error that names the limitation is strictly more honest than a runtime handshake error whose message points at TLS rather than at config.** If a `ldap://` + StartTLS deployment ever appears, the fix is two lines — set `ServerName` to the URL's host on the **StartTLS config only** — and it does not contradict the `ldaps://` finding above, because it is a different `crypto/tls` entry point. Recorded in §5's follow-ups.

**Consequence that improves the plan elsewhere.** v8 listed "a live LDAP bind round-trip against a real directory" as *blocked on lab hardware*, alongside the WebAuthn ceremony. That is no longer true: the directory is up and trusted. The live-bind test moves from "indefinitely skipped" to an **env-gated integration test** (task 3.8b) that runs whenever `MULTISSH_TEST_LDAP_URL` and a test credential are present. Only the WebAuthn-with-real-authenticator ceremony remains genuinely blocked.

## 1. RALPLAN-DR Summary

*(Regenerated for round two. v8's summary was written for a scope that included the module port; that scope is merged and gone.)*

### Principles

- **P1 — Auth is a platform capability; modules stay auth-unaware.** The package lands at `internal/platform/auth`, the gate is applied once in `cmd/server/main.go` at registration, and `multissh.Build()` takes no auth parameter and returns a handler with no auth middleware. A module must not be able to express "I forgot my gate".
- **P2 — Deny by default; fail closed, scoped to the protected set.** The gate's zero value protects everything. An auth-construction failure 503s the modules that were supposed to be protected — never a warning, never a silent fallback to `NoAuth{}` — and never the other five, which have no relationship to the failure.
- **P3 — Standard mechanisms for trust; no bespoke crypto and no disabled verification.** `ldaps://` verifies against the system trust store (§0A). WebAuthn origins are validated by the library plus our own `rp_id` non-empty check. No `InsecureSkipVerify` in any default, no custom CA pool, no hand-rolled comparison where a library exists.
- **P4 — One implementation of each security predicate, binary-wide.** `sameOrigin` exists once, in `internal/platform/middleware`, and is called by the HTTP write gate, the terminal WebSocket upgrader and the broadcast-progress upgrader. Two copies of a security predicate is how they drift; today there are already two (§0 item 3).
- **P5 — Round one's merged behavior is the baseline and stays green.** Every phase compiles and tests green on its own, and `go test -race ./...` including all of `internal/multissh` passes at every phase gate — not only at the end.

### Decision Drivers (top 3)

1. **D1 — FR-A3/A4/A5 are hard acceptance gates.** AC-6 requires `secure_mode: true` + `auth.mode: "ldap"` to produce a 401 on `/api/*` **and a rendered login page**. No design that defers LDAP login satisfies it. This is what forces the auth work to be real rather than structural.
2. **D2 — R9 is an open, exploitable defect, and it is independent of auth.** The cross-origin write gate closes a live hole in a module that executes shell commands on remote hosts, and it does so whether or not anyone ever configures LDAP. It should not be held hostage to the auth stack's schedule — hence the phase ordering below puts it first.
3. **D3 — The ported auth stack has zero upstream tests and will front all six modules.** `reference/multissh/internal/auth` ships no `_test.go` files. Under O-1 that code stands between the network and every module in the binary. Coverage (task 3.8) is the acceptance gate for this phase, not the port itself.

### Viable Options

#### Axis 1 — Where the auth stack lives

**Option E — `internal/platform/auth`, gate applied at registration (CHOSEN).**
Port `reference/multissh/internal/auth/{auth,service,store,ldap,middleware}.go` plus `server/auth_handlers.go`'s handler bodies into a new platform package with zero multissh coupling. Top-level `auth` config section; `auth.protected_modules` opt-in; `multissh.secure_mode` retained as an alias.

- Pros: one LDAP integration, one session implementation, one login flow for all six — the operator's stated end state, reached directly. The gate is applied in one place, so "a module registered without its gate" is a single-site invariant. Enrolling a second module later becomes a frontend task, not another backend lift.
- Cons: largest scope item in the plan; new top-level config surface; deeper edits to `cmd/server/main.go` and `internal/platform/config`; raises the untested-auth-stack risk from Med to High by widening its blast radius from one module to six; multissh's URL-shape assumptions must not leak into a platform-addressed predicate (this is C4, the most expensive defect the v8 iterations found).

**Option E′ — `internal/multissh/auth`, module-local, lift later.**
Port the stack where it came from; gate inside `multissh.Build()`; lift to platform when a second module actually needs it.

- Pros: genuinely the lower-risk build. Five of the six defects v8's iterations had to fix (mode route vanishing, `maxSessions` unable to cross the package boundary, the multissh-shaped public-path predicate, five gateable modules with no login UI, the silently-ungated module) **exist only because auth was generalized before a second consumer existed.** Delivers identical operator-visible behavior today: multissh gated, five modules untouched. The eventual lift is cheaper, because it extracts an interface from two real implementations instead of guessing one from zero.
- **Invalidation:** declined on operator decision O-1 ("we want to land this for all modules rather than wait — DRY all the way"), and because `internal/platform/auth` is where this code ends up regardless; migrating a security-critical package once beats migrating it twice. **This is a sequencing objection, not a destination objection, and it is not dismissed** — it is recorded in full as the standing antithesis (§6) and is the first thing to reconsider if schedule pressure appears.

**Option E″ — Front the binary with an external identity proxy** (Authelia / oauth2-proxy / nginx `auth_request`) and write no Go auth at all.

- Pros: no LDAP or WebAuthn code in this repo; no `go.mod` growth; passkeys, session management **and brute-force lockout** come from a maintained project rather than from an untested ported package; nginx already sits in front, so the insertion point exists. **The lockout point is real and is a genuine advantage of this option** — the chosen design has none in the reference and therefore has to build it (R17). Recorded honestly rather than credited to the rejected option and then forgotten.
- **Invalidation:** fails FR-A3/A4/A5 as written — they specify `POST /api/auth/login`, `GET /api/auth/session`, `auth.mode`, `requiredGroups` and `passkeyStorePath` as properties of *this* binary's config and API, and AC-6 gates on `secure_mode: true` producing that behavior. It also contradicts NFR-1's one-binary/one-process motivation and adds a second daemon to a deployment whose entire premise was collapsing six processes into one. Rejected on requirement coverage and on deployment shape, **not** on merit — it is the right answer for a product, and it is the answer to revisit if the ported auth stack ever proves to be a maintenance sink.

#### Axis 2 — Where the origin control lives

**Option F — Same-origin policy in `internal/platform/middleware`, all six modules (CHOSEN).**
`Wrap` stops emitting the wildcard and reflects ACAO only same-origin; a second middleware rejects every non-`GET`/`HEAD` cross-origin request with 403 at any path on any module; `sameOrigin` lifts out of both multissh copies into the shared package.

- Pros: closes R9 for the module that actually executes commands, and closes it identically everywhere else for free. One predicate, one implementation (P4). Any future module inherits the policy rather than choosing it. This is operator decision O-3.
- Cons: a real NFR-5 exception — the other five modules' response headers change and their write routes gain a 403 path. It makes `Host`-preserving proxy configuration load-bearing for **all six** modules where today it is load-bearing for none (R1) — one wrong `proxy_set_header` line turns every write in todo and grocery into a 403, as collateral from work on a different module.

**Option F′ — Same control, scoped to multissh only.**

- Pros: blast radius of a proxy misconfiguration stays at one module. R9's actual danger — remote command execution — is entirely multissh's; todo's worst cross-origin outcome is a scrambled column list.
- **Invalidation:** directly reverses O-3, which the operator chose explicitly before v4 and reaffirmed with "DRY all the way". It also puts the load-bearing control in a package only one module can reach, which is what v4 did and what v5 reversed. Recorded as the mitigation-in-waiting if R1 bites in practice: **4.6b may be narrowed to multissh without reopening R9 for multissh**, which is the only module where R9 is severe.

**Option F″ — CSRF tokens instead of an origin check.**

- Pros: the textbook answer; immune to `Host` rewriting, so it dissolves R1 entirely.
- **Invalidation:** requires a token endpoint, per-form/per-request token plumbing in **six** SPAs (five of which this work is otherwise not allowed to touch, §7.8), and a session to bind the token to — which does not exist when `auth.mode: "none"`, the default and the exact configuration R9 is dangerous in. An origin check needs no session and no frontend change at all. Rejected as strictly more work for strictly less coverage in the configuration that matters.

### Chosen combination

**E + F:** platform-owned auth gate, platform-owned same-origin policy.

## 1A. Pre-mortem (deliberate mode)

*It is March 2027. Round two shipped. Three ways it went wrong.*

**Scenario 1 — "Five modules were behind a login page that was never actually mounted."**
The operator stood up LDAP, added `grocery` and `todo` to `auth.protected_modules`, restarted, saw the login page on multissh, and considered it done. Grocery and todo served unauthenticated the whole time: the gate is applied in `cmd/server/main.go`'s registration loop, and the branch that consults `protected_modules` was only ever exercised for multissh, whose membership arrives via the `secure_mode` alias on a *different code path*. Every test stayed green, because the auth test named multissh explicitly instead of iterating the configured list.
*Root cause:* under O-1 the enforcement point moved from the module to the dispatcher, and the tests did not move with it.
*Task changes:* 4.9's 401 test **iterates `protected_modules` from the loaded config**; the `secure_mode` alias is resolved into that list *before* the loop, so both routes into membership share one code path; the test probes **a data route the module actually serves** (from 0.2b's table), never a synthetic `/api/…` path that the catch-all would answer anyway.

**Scenario 2 — "The LDAP connection was unverified for a year, and the config said `ldaps://`."**
The operator's config named `ldaps://ldap.cmdhome.net`. Everything worked. Eighteen months later someone noticed `insecure_tls: true` in `unified-webapp-example.json`, copied from the reference's `applyAuthDefaults` during the port because "that's what the defaults were". Every bind since had accepted any certificate any host on the LAN cared to present.
*Root cause:* an insecure default carried across by a "port verbatim" instruction that never named it. (Earlier drafts added a second cause — a hostname-mismatch failure from an unset `ServerName` — which §0A has since established does not exist; `crypto/tls` derives the name from the dial address.)
*Task changes:* §0A names `applyAuthDefaults`'s `InsecureTLS = true` explicitly as a thing not to port; `insecure_tls` defaults false and **logs a WARN at load when true**; 3.8's dial test asserts the `tls.Config` handed to the dial under a default `ldaps://` config has `InsecureSkipVerify == false`; 3.8b's live bind proves system-trust verification end to end; 6.2 documents the knob as exotic-deployments-only.

**Scenario 3 — "The origin gate broke todo, and nobody connected it to the multissh work."**
Two weeks after round two merged, the operator's grocery list stopped saving. So did todo. Reads worked; every write 403'd. The nginx config had `proxy_set_header Host $proxy_host` on those vhosts — as it had for years, harmlessly, because nothing in the binary had ever compared `Origin` to `r.Host`. The change that made it matter shipped under a plan titled "multissh auth".
*Root cause:* O-3 converts a dormant proxy misconfiguration into a five-module outage, and the failure surfaces far from its cause.
*Task changes:* 4.6b logs the observed `Origin`/`Host` pair on **every** rejection, so one log line diagnoses it; 6.2's proxy note is marked **load-bearing, not advisory**, and names the exact `proxy_set_header Host $host` requirement per vhost; the 6.4 acceptance pass exercises a write on **todo and grocery through the real proxy**, not just multissh through `localhost`; §5 records the F′ narrowing (multissh-only) as the pre-authorized rollback.

**Scenario 4 — "The limiter never limited anything, and nobody noticed until the directory account locked out."** *(New in v12; the pre-mortem predated 3.9 and 4.11 and had no scenario for either.)*
The operator's nginx vhost had a bare `proxy_pass` — no `proxy_set_header X-Forwarded-For` line, because nothing had ever needed one. 3.9's limiter saw a trusted `RemoteAddr` (nginx on loopback) and **no `X-Forwarded-For` header**, which is the specified fail-**open** branch: it declined to limit, logged a once-a-minute WARN nobody was grepping for, and passed every login straight through to the bind. Eight months later a stuck browser tab retried a stale credential for a weekend and locked out the operator's AD account — the exact outcome R17's directory-lockout half exists to prevent, from a control that had been inert since the day it shipped.
*Root cause:* the mitigation's correctness depends on a proxy config line the plan never required, and its failure mode is silence.
*Task changes:* **6.2 mandates `proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;`** alongside the `Host` line and states the **trusted-hops-must-append** invariant (C4); **4.9's boot summary reports the limiter's armed state** (`login-limit=armed(trusted_cidrs=2)`), so an inert limiter is visible on every restart rather than only by grepping for an absence; **6.4 asserts the word `armed` appears in the boot log** when auth is enabled, and asserts the header is actually present and keying correctly, not merely that a 429 eventually appears; **§4 records the map-cap eviction bypass honestly** (C5) rather than presenting the cap as a clean mitigation.

**A.1 — Lift `sameOrigin` into `internal/platform/middleware`.** Round one shipped **two** copies: `internal/multissh/sshproxy/proxy.go:303` (+ `originHost` at `:322`) and `internal/multissh/broadcast.go:388` (+ `originHost` at `:403`). **The audit-line seam — the non-obvious half of this task.** Both rejection paths also **log**: `sshproxy/proxy.go:315` calls `Auditf(...)` and `broadcast.go:399` calls `sshproxy.Auditf(...)`. `Auditf` lives in `internal/multissh/sshproxy/audit.go:12`. A naive lift forces one of three bad outcomes: `internal/platform/middleware` imports `internal/multissh/sshproxy` (inverts the layering this whole plan exists to establish); the audit line is silently dropped (**regresses `audit_test.go:129-133`**, which asserts the `origin=`/`host=` line appears); or the behavior quietly diverges between the two upgraders. **Specified fix — take a logger, do not take a dependency.** The lifted predicate is constructed with a logging func field:

```go
// internal/platform/middleware
type OriginChecker struct {
    Logf         func(format string, args ...any) // nil → log.Printf
    RejectFormat string                           // "" → middleware's platform default
}
func (c OriginChecker) SameOrigin(r *http.Request) bool
```

**Two fields, not one — and this was v11's second blocking defect.** v11 specified only `Logf`, on the assumption that the two rejection paths differed merely in *sink*. **They do not: they differ in the literal format string.** `sshproxy/proxy.go:315` emits `"ws upgrade rejected origin=%q host=%q"`; `broadcast.go:399` emits `"broadcast ws upgrade rejected origin=%q host=%q"` — note the leading `broadcast ` token. A single-field `OriginChecker` must therefore collapse both to one format, silently breaking one of them, and **neither existing test would catch it**: `internal/multissh/audit_test.go:129-133` asserts only the `origin=`/`host=` substrings (which survive the collapse), and `sshproxy/audit_test.go:136` asserts a substring that happens to match *both* formats. v11's stated criterion ("byte-identical… if any assertion string changes, the logger seam failed") was consequently unmeetable by construction.

**All three format strings, named here so none is left to inference:**

| Constructor | `RejectFormat` |
|---|---|
| `sshproxy` (`proxy.go:61` `CheckOrigin`) | `"ws upgrade rejected origin=%q host=%q"` |
| `broadcast` (`broadcast.go:91` `CheckOrigin`) | `"broadcast ws upgrade rejected origin=%q host=%q"` |
| **A.2's dispatcher middleware** | `"cross-origin rejected origin=%q host=%q"` |

`sshproxy` and `broadcast` each construct theirs passing `Auditf` (resp. `sshproxy.Auditf`) as `Logf` **and their own format above as `RejectFormat`**, so each emitted audit line is **byte-identical to today's**. A.2's middleware passes `Logf` nil (or the platform logger) and the third format — a dispatcher-level rejection is not a multissh audit event, and it needs its **own distinct string** because 6.2's detection recipes grep for exactly `cross-origin rejected`; under v11's single-format design that grep would have matched nothing, forever.

**`OriginChecker` must NOT log on the accept path.** Only rejections emit a line. A same-origin upgrade is the overwhelmingly common case and logging it would flood journald on every page load, drowning the very rejections 6.2's recipes are counting.

**Acceptance criterion — stated behaviorally, because the v10 wording was impossible.** v10 required "`audit_test.go` passes unchanged … unedited except its import path". That cannot hold: `internal/multissh/audit_test.go:129` calls the **unexported, package-level** `sameOrigin(req)` in `package multissh`, which this task **deletes**. The replacement is `middleware.OriginChecker{Logf: sshproxy.Auditf, RejectFormat: "broadcast ws upgrade rejected origin=%q host=%q"}.SameOrigin(req)` — a change of **call form**, not of import path. The real criterion:

> **The full rejection line each call site emits is byte-identical to the line it emits today, `broadcast ` prefix included.** Only the call form in the tests is updated, to construct an `OriginChecker` with the site's `Logf` and `RejectFormat`. If any emitted line changes, the seam failed and the task is not done.

**Two tests must stay green, and one of them must be strengthened.** v10 named only the first:
- `internal/multissh/audit_test.go:129-133` — pins `broadcast.go:399`'s rejection line and calls the predicate directly (hence the call-form edit above). **This task strengthens its assertion from a substring check on `origin=`/`host=` to a check on the FULL emitted line, including the leading `broadcast ` token.** That strengthening is a named deliverable of A.1, not an optional tidy-up: it is the only thing standing between a future refactor and a silent collapse-to-one-format regression, which is precisely the defect v11 shipped.
- **`internal/multissh/sshproxy/audit_test.go:136`** — pins `proxy.go:315`'s format and reaches it through a **real rejected WebSocket dial**, so it needs no edit at all. It is the stricter of the two end to end, but note that its assertion is a substring that also matches the broadcast format — which is why the strengthening above is required rather than relying on this test alone.

**One-sentence note on the predicate's limits:** `originHost` (`proxy.go:322`) compares `u.Host` only and is therefore **scheme-blind** — `http://x` and `https://x` are the same origin to it. After A.2 this predicate is the binary's **primary** CSRF defense — not its only one: `setSessionCookie` hardcodes `SameSite=Lax` (`auth_handlers.go:239`), which independently blocks cross-site cookie-bearing POSTs on **authenticated** routes. The gap the origin check alone covers is therefore the unauthenticated default config (`auth.mode: "none"`), which is precisely where R9 is dangerous. The scheme-blindness is recorded here rather than discovered later; it is accepted for a LAN deployment behind a TLS-terminating proxy.

**A.2 — Reject cross-origin state-changing requests, server-side, all six modules.** New middleware in `internal/platform/middleware`, covering **every non-`GET`/non-`HEAD` request at any path**:
- `Origin` present and its host[:port] ≠ `r.Host` → **403**, body never decoded, module handler never reached. **Log the observed `Origin`/`Host` pair** (scenario 3), via an `OriginChecker` carrying `RejectFormat: "cross-origin rejected origin=%q host=%q"` (A.1) — the distinct dispatcher-level string 6.2's grep recipes search for.
- `Origin` absent → **permitted** (curl, scripts, the 6.4 acceptance pass). **Why this is safe rather than a loophole:** every browser engine in current use sends `Origin` on `POST`, `PUT`, `PATCH` and `DELETE` unconditionally — it is not suppressible from page script, and it is sent even for `Content-Type: text/plain` simple requests, which is the exact shape R9 exploits. An absent `Origin` therefore means "not a browser", and a non-browser client is not acting under an attacker's page. This control is scoped to the confused-deputy threat (§4's stated model), not to a direct attacker who can craft arbitrary requests and for whom no origin check of any kind would help.
- **`Origin: null` → 403.** Sandboxed iframes, `data:` documents and some redirect chains send the literal string `null`. `originHost("null")` returns `"null"`, which never equals `r.Host`, so the existing predicate already **fails closed** here with no special-casing. Stated explicitly because this section enumerates the empty-`Origin` case and silence would read as an oversight; a test pins it.
- **No path condition.** A `/api/*` prefix filter would be a filter on multissh's URL style, not on danger — per A.0b, todo's entire write surface is non-`/api/`. The method is the signal. There is no module here for which a cross-origin write is legitimate.
- **Application point and composition order — specified, because A.2 and A.3 both have opinions about `OPTIONS`.** A.2 is a **separate middleware** from `Wrap`, not a merge into `cors.go`, and **A.2 runs outermost**: `middleware.RejectCrossOriginWrites(middleware.Wrap(dispatch))`, replacing the existing single `middleware.Wrap(dispatch)` call at `cmd/server/main.go:72`. This ordering is load-bearing. A.3 keeps `Wrap`'s `OPTIONS` 204 short-circuit; A.2 403s every non-`GET`/`HEAD` request including `OPTIONS`. **A foreign-origin preflight must therefore reach A.2 first and be 403'd there — `Wrap`'s `OPTIONS` short-circuit is only ever reached same-origin.** Reversing the order would have `Wrap` hand a foreign preflight a 204 before A.2 saw it. One application for the whole binary, before host dispatch, and necessarily outside every module's future `Gate` — so a cross-origin write is 403'd before any credential is examined.

**Why removing the ACAO header is not the fix.** ACAO is a *response* header: it governs whether the attacker's page may **read** the reply. The request still executes. `POST /api/broadcast` with `Content-Type: text/plain` is a CORS **simple request** — no preflight fires, so there is nothing for a missing ACAO to block — and `handleBroadcastPost` decodes with `json.NewDecoder` and proceeds, checking neither `Origin` nor `Content-Type`. **A.2 is the load-bearing half; A.3 is defense-in-depth for the read half.**

Tests: `POST /api/broadcast` with `Origin: https://evil.example` and a routed multissh `Host` → 403 **and no job created** (a status code alone does not prove the handler was not reached); matching `Origin` → proceeds; absent `Origin` → proceeds; foreign-origin `OPTIONS` preflight not granted. **Named-route assertions on other modules, from A.0b:** foreign-origin `POST` to todo's `/config/columns` and `/items/{subject}` and to slideshow's `/api/control` each 403, and the todo case additionally asserts the column list is **unchanged** afterwards. These are named routes, so the test fails if the middleware is ever re-scoped to a path prefix.

**A.3 — `Wrap` becomes same-origin.** Rewrite `internal/platform/middleware/cors.go`: drop the wildcard at `:8`; reflect `Access-Control-Allow-Origin` only when the request `Origin`'s host[:port] equals `r.Host`; always emit `Vary: Origin`; keep the `OPTIONS` 204 short-circuit but only for same-origin. `Wrap` stays applied **once** around the dispatcher — no per-module wrapping.

Tests: same-origin → ACAO reflected + `Vary: Origin`; foreign origin → **no** ACAO; absent `Origin` → unaffected; and **a regression test that all six modules still serve their own same-origin pages normally** (the operator's explicitly requested regression test).

If one ever must, it implements `Hijack()` by delegation. Test: a real WebSocket upgrade through the full `Wrap` → A.2 → dispatch → module chain succeeds.

**B.3 — Validation that refuses to start (fail-open shapes).**

- **`auth.mode` not in `{"", "none", "ldap", "ldap_passkey"}` — an unknown mode value is a load error.** *(New in v11.)* This is the **fifth** fail-open shape and it defeats all four of the others. - `multissh.secure_mode: true` **and** `auth.mode: "none"` — a config that reads as secured, wraps everything in `NoAuth{}`, shows no login and reports no error. This is pre-mortem scenario 1's shape.
- `auth.protected_modules` non-empty **and** `auth.mode: "none"` — same failure, stated the other way round.
- `auth.mode ∈ {"ldap","ldap_passkey"}` with an empty `ldap.url` or empty `base_dn`. Such a config constructs cleanly (see B.5) and then 401s every login forever, reading as "LDAP is broken" rather than "LDAP is unconfigured".
- **`auth.mode: "ldap_passkey"` with an empty `auth.passkey_store_path`** *(new in v12, C7)*. `applyAuthDefaults` is not ported, so this field has no default and stays empty; `newPasskeyStore` then errors inside `EnablePasskeys` and the protected modules 503. It fails closed either way, but a load error naming `passkey_store_path` is strictly more legible than a 503 whose reason names a store the operator never configured.
- `auth.mode: "ldap_passkey"` with empty `passkey.rp_id` or empty `passkey.origins`. **This check is ours to write:** `go-webauthn` validates `RPID` only when it is non-empty (`webauthn/types.go:141`) and errors solely on empty `RPOrigins` (`:166`), so an empty `rp_id` sails through its validation and fails later at ceremony time.
- **`auth.ldap.start_tls: true` together with `auth.ldap.insecure_tls: false` — rejected as an unsupported combination (§0A).** *(New in v11; this is the F1/M2 resolution.)* The error message must name the limitation rather than the symptom: *"start_tls with certificate verification enabled is not supported: go-ldap's StartTLS path calls tls.Client, which cannot derive ServerName from the dial address, and crypto/tls rejects a config with neither ServerName nor InsecureSkipVerify. Note this is an **error**, not B.4's WARN: the WARN case is `start_tls: true` with a `ldaps://` URL, which is merely redundant; this case cannot work at all.
- a name in `auth.protected_modules` that is not present in `host_routing` — an unreachable gate is a typo, and typos here fail open. **Only this half is implementable at load;** the "is it a known module name" half lives in `cmd/server/main.go`'s `buildModule` switch and runs at registration (4.9), because duplicating that switch into the config package would drift the moment a seventh module is added.

*(Recorded, deliberately not rejected:* `auth.mode ∈ {"ldap","ldap_passkey"}` with an **empty resolved protected set** is the third member of this family. 4.3's conjunction correctly yields `NoAuth{}`, and the symptom — no login page appears anywhere — is immediate and unmissable. **3.1c — Define `auth.Gate`.** This is the central new abstraction, and v8 described it in three fragments while defining it in none — two competent executors would have produced materially different types, one of them fail-open. Define it here, in full:

```go
type Gate struct {
    Provider        Provider       // NoAuth{} when this module is not protected
    Service         *Service       // nil when Provider is NoAuth{}
    CookieSecure    bool           // from cfg.Auth.CookieSecure (4.9)
    PublicPrefixes  []string       // 4.9
    PrivatePrefixes []string       // 4.9
    ModeExtras      map[string]any // 3.6b; multissh passes {"maxSessions": N}, others nil
    LoginLimiter    *LoginLimiter  // 3.9; nil → no limiting (unprotected modules)
}

func (g *Gate) Wrap(next http.Handler) http.Handler
```

**`Wrap` builds its provider chain once, at wrap time, not per request.** `protected := g.Provider.Middleware(next)` is constructed in `Wrap`'s body and closed over; step 3 below calls the **already-constructed** handler. v10's step 3 read "delegate to `g.Provider.Middleware(next)`", which invites an allocation and a middleware re-construction on every single request through every module in the binary. One line's difference; state it so it is not left to taste.

`Wrap` returns a handler that, in order:
1. Serves `GET /api/auth/mode` itself, **always**, whatever the provider is.
2. Serves the other **nine** `/api/auth/*` routes **only when `g.Service != nil`**.
   - **2a. The three unauthenticated credential-verification routes pass through `g.LoginLimiter` first** (3.9) — `POST /api/auth/login`, `POST /api/auth/passkeys/login/begin`, `POST /api/auth/passkeys/login/finish` — *before* the handler is invoked and therefore before any LDAP dial or any challenge allocation. *(v12, Architect C6: v11 limited only `/login`, leaving two equally unauthenticated endpoints wide open — and `passkeys/login/begin` additionally stores a challenge in a map that `loadChallenge` only deletes **on read**, so unread entries accumulate without bound.)* **Step 2a has two halves, and v11 specified only the first:**
     - **Read (pre-request).** Derive the limiter key **once** here, by 3.9's XFF/RemoteAddr rules, and ask the limiter. Over budget → `Wrap` writes **429** with `Retry-After` and returns; the handler is never reached.
     - **Carry (pre-request).** Otherwise, place the derived key into the request context under a package-private key and call the handler with it. **The key is computed once, here, and never recomputed inside the handler** — two derivations of the same key from the same request is two places for the XFF logic to drift, and the whole control depends on that logic being right.
     - **Write (post-request)** happens inside `handleAuthLogin` via 3.1's third exception; see 3.9.
     When `g.LoginLimiter` is nil — which is every unprotected module, since no login endpoint is mounted there at all — this step is a no-op. These three routes are R17's enforcement points and the only ones; **no other route is limited.** When `Service` is nil these paths are not registered at all and fall through to `next`. *(Count reconciled against source: `reference/.../server.go:96` mounts `GET /api/auth/mode` unconditionally, and `:98-106` mount **nine** guarded routes — session, login, logout, passkeys list, register begin/finish, login begin/finish, delete — served by **nine** distinct handlers. **Ten routes in total.** Earlier drafts said "eight" in this step and "eight of nine handlers" in 4.9; both were wrong, and the correct figure is nine and nine.)*
3. For everything else: if `g.isPublic(r)`, call `next`; otherwise call `protected` — the handler built once above from `g.Provider.Middleware(next)` — which enforces the session and 401s.

**Step 2's guard is the point of this task.** It reproduces `reference/.../server.go:97`'s `if s.authSvc != nil`, which is what makes FR-A3's "when auth is off, `GET /api/auth/mode` is the only auth route that exists" true. Without it, a `NoAuth` Gate mounts `POST /api/auth/login` with a nil `*Service`, and `handleAuthLogin` (`auth_handlers.go:73`) dereferences it: an **unauthenticated 500 on all six modules under the default config**. 3.8 tests this branch directly.

*(Ordering note: `/api/auth/` is the first clause of the predicate, so the mode route would be public even if step 1 ran last. Handling it first removes the dependency on that ordering rather than relying on it.)*

**3.1e — Write `auth.FromConfig`; it does not exist and nothing else creates it.** 4.9 calls `auth.FromConfig(cfg.Auth)` as though it were part of the ported stack. **It is not.** The reference's equivalent is `buildAuth()` in **`reference/multissh/cmd/multissh/main.go`** — binary-local glue, not a member of `internal/auth`, so "port `internal/auth` verbatim" never brings it across. ```go
func FromConfig(c config.AuthConfig) (Provider, *Service, *LoginLimiter, error)

*Login rate limiter (R17):* 3.9's **five** cases — the counter reaches `maxFailures` → the next attempt is 429 **with no dial attempted**; only credential-rejection outcomes are recorded (a 400 malformed body does **not** count); success resets and the lockout expires on the injected clock; key isolation through the proxy including the spoofed-leftmost-`X-Forwarded-For` case; and the passkey login routes are limited on the same key as `/login`. See 3.9 for the full specification, including the `RecordFailure`/`RecordSuccess` write path that v11 omitted entirely.

*Session and middleware (FR-A4):* no cookie → 401 on a private route; valid cookie → passthrough; `SessionTTL`-expired → 401; `IdleTTL`-expired → 401 (**inject the clock via 3.1f's `now` field, do not sleep**); logout invalidates and the cookie is not replayable; `HttpOnly` always set and `Secure` follows `cookie_secure`. **`SameSite` is not configurable** — `setSessionCookie` hardcodes `http.SameSiteLaxMode` (`auth_handlers.go:239`); port that verbatim and assert it. The cookie sets **no `Domain`**, which is what makes sessions host-scoped (see §4).

*LDAP (FR-A4, §0A), against the 3.1b fake:*
- Bind failure → 401, **no cookie set**; bind success → cookie set.
- `required_groups` mismatch → 401 even on a successful bind; match → pass.
- `NoAuth` provider → every request passes, `Mode()` reports `"none"`.
- **TLS posture (§0A):** with a default config naming an `ldaps://` URL, the `tls.Config` handed to the dial has **`InsecureSkipVerify == false`**; with `insecure_tls: true` it is `true`, and the load-time WARN was emitted. **That is the whole assertion.** Do **not** additionally assert a non-empty `ServerName` — earlier drafts required it, and it is wrong: go-ldap leaves `ServerName` empty by design and `crypto/tls` supplies the dial hostname itself, so the assertion would fail against correct, secure behavior and invite someone to "fix" it by hardcoding a name. `InsecureSkipVerify == false` is the real regression guard, and 3.8b is the proof that verification genuinely succeeds end to end.

*Passkeys (FR-A5, O-2):* registration- and assertion-option generation produces a well-formed challenge for the configured `rp_id` — **asserted against a literal expected string, never against the config value the test fed in**, which is a tautology when the value is empty; challenge storage is single-use (replay rejected) and expires; an assertion from an origin outside `passkey.origins` is rejected; credential-store round-trip survives a store restart; and `mode: "ldap_passkey"` with empty `rp_id`/`origins` is a **`config.Load` error (B.3)**, not a construction error.

**Scope note on `rp_id`.** It is single-valued and must be a registrable-domain suffix of every origin in `passkey.origins`. Modules are dispatched by Host header, so covering all six would mean setting it to their shared parent domain, scoping credentials to that parent. Since passkeys front **multissh only** for now (§4, M9), set `rp_id` to multissh's own hostname and list only that origin. Widening it is a decision for when a second module actually gets a login page.

**3.8b — Live LDAP bind, now unblocked (§0A).** v8 listed this as blocked on lab hardware. The directory is up and its certificate is trusted, so it is not. Write it as an **env-gated integration test**: skips unless `MULTISSH_TEST_LDAP_URL` (and a test DN/password) are set, and when set, performs a real bind against `ldaps://ldap.cmdhome.net` **through the production code path with `insecure_tls: false`** — which makes it the end-to-end proof that system-trust verification works, not merely a mock assertion. Document the invocation in 6.2.

**Still genuinely blocked:** an end-to-end WebAuthn ceremony with a real authenticator over real HTTPS. Written against the fixture seam, `t.Skip`ped with the missing dependency named, listed in 6.2. That is the honest boundary — and it is now a list of one, not two.

**3.9 — Login rate limiter (owns R17; new in v11).** In v10 this control existed **only as prose in the R17 risk row**: no package, no task, no clock, no position in `Gate.Wrap`, no tests in 3.8's enumeration, no line in §2A, no mention in any Verify step. Both reviewers flagged it independently as the same defect. It is now a task, and it is **mitigated rather than accepted** for the reason R17 gives: a defect in *this* binary must not be able to lock out the operator's own directory account, which is infrastructure outside this binary's blast radius.

**Location.** `internal/platform/auth/loginlimit.go`, type `LoginLimiter`, held by `Gate.LoginLimiter` and consulted at `Gate.Wrap` **step 2a** (3.1c). Constructed by `FromConfig` (3.1e), returned as its **third** value, alongside the `*Service` — non-nil exactly when the `*Service` is non-nil, since the login routes do not exist otherwise. **One instance, shared by every `Gate`** (3.1e).

**The write path — v11 had none, and this is the defect both reviewers found.** *(New in v12; CRIT-1.)* v11 specified only `Gate.Wrap` step 2a, which is a **pre-request check**: it reads accumulated state. But whether a login *failed* is a **post-request fact**, known only inside `handleAuthLogin` (`reference/multissh/internal/server/auth_handlers.go:64-87`) — and v11's 3.1 forbade modifying that handler beyond its two named exceptions. So nothing anywhere incremented the counter. 3.8's first test ("`maxFailures` failures → the next attempt is 429") was **unwritable**, and R17's row claimed a mitigation that could not fire.

**Mechanism, decided between the two the reviewers offered — the handler records, the gate derives.** `handleAuthLogin` gains **exactly two lines**, and this is 3.1's **third assigned exception**:

- `LoginLimiter.RecordFailure(key)` on the auth-error branch;
- `LoginLimiter.RecordSuccess(key)` immediately after `setSessionCookie` succeeds.

The `key` is **not** recomputed here — it is read from the request context, where `Gate.Wrap` step 2a placed the single derivation (3.1c). The alternative considered and rejected was having `Wrap` inspect the handler's response status through a wrapping `ResponseWriter`: that is more code, it re-derives the failure signal from an HTTP artifact rather than reading it at the source, and A.4 already forbids wrapping `ResponseWriter` in this binary's request path.

**Which outcomes count as a failure — stated explicitly, because getting this wrong is itself an attack.**

- **Counted:** an actual credential rejection — `ErrLDAPAuth` and `ErrLDAPForbidden` per `writeAuthError`'s mapping. These are the outcomes that mean "someone guessed and was wrong", which is the only thing worth rate-limiting.
- **NOT counted — a 400 malformed body.** If a malformed request incremented the counter, an unauthenticated attacker could **poison an honest key's lockout with garbage requests**, spending nothing and never touching the directory. That converts the mitigation into a targeted denial of service against whichever client the attacker can make the key resolve to.
- **NOT counted — directory-unreachable / dial / network errors.** *(This was the Critic's open question; the plan answers it rather than leaving it open.)* If a dial failure maps to a countable outcome through `writeAuthError`, then **an LDAP outage locks out break-glass recovery**: every attempt fails for reasons having nothing to do with the credential, the counter fills, and the operator is 429'd out of the login screen at exactly the moment §4's break-glass procedure is being exercised. The executor must **check `writeAuthError`'s actual mapping** and, if a dial error shares an error value with credential rejection, split them before wiring `RecordFailure` — the limiter counts *credential rejection only*.
- A 429 from step 2a records nothing. It never reaches the handler, so it is not an attempt; see the trigger-point statement below.

**Its own clock, not `Service`'s.** 3.1f's `now func() time.Time` is a **private field on `*Service`**, and a limiter fronting an HTTP handler is not a `Service` method — it cannot reach that field, and widening `Service`'s seam to serve it would be the wrong shape. **Resolution: promote a tiny shared type** in the same package —

```go
type clock struct{ now func() time.Time }
func (c clock) Now() time.Time { if c.now != nil { return c.now() }; return time.Now() }
```

— and give **both** `Service` and `LoginLimiter` a `clock` field. 3.1f's six call sites become `s.clock.Now()`; the limiter uses `l.clock.Now()`. Unexported, set only by tests in-package, still no config surface and no DI framework. *(This supersedes 3.1f's "one func field" wording by exactly one type declaration; 3.1f's call-site list is otherwise unchanged.)*

**Mechanism — flat 429, and explicitly NOT an escalating delay.** v10's R17 row offered "an escalating delay (or a flat 429)" as equivalent options. **They are not equivalent and the delay option is withdrawn:** an escalating delay holds a goroutine and a connection open for the duration of the penalty, so an attacker sending failures faster than they expire converts the *mitigation* into the DoS. The limiter never sleeps and never blocks. It is:

```go
// in-memory, mutex-guarded
map[string]struct{ failures int; windowStart time.Time }
```

**Constants, fixed in code, no config surface:** `maxFailures = 10`, `window = 15 * time.Minute`, `lockout = 15 * time.Minute`.

**The trigger point, stated once and normatively — every other mention in this document defers to this sentence.** *(v12, Critic M4: v11 stated it three mutually inconsistent ways, in 3.9, in 3.8/§2A, and in 6.4 — the last of which was internally self-contradictory, since a request that returns 429 never reaches a bind and therefore cannot itself be "a failed login".)*

> **The counter increments on each recorded failure (per the write path above). When it reaches `maxFailures` (10), every subsequent attempt returns 429 immediately, with `Retry-After`, without a bind being attempted, until the lockout window expires.**

So: ten failed logins, then an eleventh **attempt** is refused. The eleventh attempt is not a failed login; it is a refused one.

A **successful** login clears the key. Entries are evicted lazily on lookup, like sessions (§4) — no reaper, no persistence; a restart clears the state, which is acceptable at one operator on a LAN (§5 records persistence as a follow-up).

**Bounded size — and the cap is a limitation, not a clean mitigation.** *(Rewritten in v12, Architect C5.)* v11 said "cap the map at 1024 keys and drop the oldest on overflow". **That eviction rule is itself a bypass:** an attacker with access to more than 1024 distinct keys — trivial with an IPv6 allocation, or any header they can influence — floods the map until their *own* locked-out entry is evicted, and starts over. v11 also left "oldest" undefined between *insertion order* and *window start*, and those two orderings differ **exactly** in this scenario. The specified rule:

> Cap at 1024 keys. On overflow, **evict the oldest entry that is NOT currently locked out** (oldest by `windowStart`). **If all 1024 entries are currently locked out, refuse to track new keys** — new keys are not limited until a slot frees; existing lockouts remain enforced and are never evicted to make room.

This fails open for *new* keys only and never discards an active lockout, which is the right direction: the thing worth protecting is the lockout already earned. **It is recorded in §4 as an accepted scale limitation**, alongside the other single-operator-scale tradeoffs, rather than presented as a solved problem — an attacker with 1024 keys can still deny *tracking* to an honest new client, and at this deployment's scale that is acceptable and at a larger one it is not.

**The key — and this is the part that decides whether the control works at all.** Every request reaches this binary **through nginx**, so `r.RemoteAddr` is nginx's IP on every request without exception. Keying on `r.RemoteAddr` naively gives a **single global counter**, and 10 failed logins from anywhere on earth then lock out the operator — the mitigation inverted into the exact denial of service it exists to prevent. Both reviewers landed on this independently. The specified behavior:

- A new config field **`auth.trusted_proxy_cidrs []string`** (snake_case, added to B.1's tag list, validated as parseable CIDRs at load in B.3, defaulting to **`["127.0.0.1/32", "::1/128"]`** — which is what nginx-on-the-same-host presents).
- **If `r.RemoteAddr` is inside a trusted CIDR**, take the **rightmost** entry of `X-Forwarded-For` that is *not itself* in a trusted CIDR as the key. Rightmost-untrusted, never leftmost: the left of that header is attacker-controlled and a leftmost read lets an attacker mint a fresh key per request, evading the limiter entirely while still being able to poison any key they choose.
- **If `r.RemoteAddr` is NOT inside a trusted CIDR**, ignore `X-Forwarded-For` completely and key on `r.RemoteAddr` — the direct-connection case (`localhost:8080` during 6.4).
- **If the header is absent or yields nothing usable while `RemoteAddr` is trusted**, the limiter **does not limit** that request and logs a WARN once per minute. This is the deliberate fail-**open** in this design and it is the right direction here: the failure being avoided is *locking the operator out of his own lab*, and the alternative — a global counter — is a worse outcome than no limiter. R17's severity is Med, not High, and §4 records the consequence.
- 6.2 documents that a misconfigured `trusted_proxy_cidrs` disables login rate limiting rather than breaking login.

**Two nginx-side preconditions this control silently depends on** *(new in v12, Architect C4 — v11 specified the header's *interpretation* and never required the header to exist)*:

1. **nginx must be configured to send it at all.** A bare `proxy_pass` does **not** set `X-Forwarded-For`. On that — entirely plausible, and quite possibly the operator's current — deployment, `RemoteAddr` is trusted, the header is absent, and the fail-open branch below fires **on every request, forever**, with no signal louder than a once-a-minute WARN. **6.2 mandates `proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;`** and **4.9's boot summary reports the limiter's armed state**, so this is visible on every restart rather than discoverable only by grepping for an absence. Pre-mortem scenario 4.
2. **Every trusted hop must APPEND, not overwrite.** Rightmost-untrusted key derivation is only sound if each trusted proxy appends the peer it saw — which is exactly what `$proxy_add_x_forwarded_for` does. A hop using `$http_x_forwarded_for`, or passing the header through untouched, makes the **rightmost** entry attacker-controlled, which re-enables *both* attacks the trusted-CIDR design exists to prevent: minting a fresh key per request to evade the limiter, and choosing an honest key to lock out. **6.2 states this as an invariant of the deployment, not a recommendation.**

**Tests — five cases, added to 3.8's suite and §2A's Unit row:**
1. **The counter reaches `maxFailures` → the next attempt is 429 *before any bind is attempted***, asserted against the 3.1b fake by proving **no dial occurred**. That assertion, not the status code, is what proves the *directory* is protected — the half of R17 that tipped it from accepted to mitigated. **This test is only writable because of v12's `RecordFailure` write path**; under v11 the counter never moved and the test could not be written at all.
2. **Only credential rejections are recorded.** A malformed-body `POST /api/auth/login` returning 400, repeated well past `maxFailures`, leaves the key un-limited — proving an unauthenticated attacker cannot poison an honest key's lockout with garbage. If `writeAuthError` maps dial errors to the same outcome as credential rejection, assert the split: a directory-unreachable failure likewise does not count.
3. **A success resets the counter**, and the lockout expires on its own — both driven by advancing the injected `clock`, never by sleeping.
4. **Key isolation through the proxy**: two requests arriving from the *same* `RemoteAddr` (nginx) with *different* rightmost-untrusted `X-Forwarded-For` values are counted **separately**; a spoofed leftmost `X-Forwarded-For` does **not** create a new key; and an untrusted `RemoteAddr` sending an `X-Forwarded-For` has the header **ignored**. This is the test that would have caught the global-counter inversion.
5. **All three limited routes share one key** (C6): failures recorded via `POST /api/auth/login` cause `POST /api/auth/passkeys/login/begin` from the same key to 429, and vice versa — so an attacker cannot reset their budget by switching endpoints.

**Verify Phase C:** `go test -race ./internal/platform/auth/... ./internal/platform/config/...` green; `go build ./...`; **`CGO_ENABLED=0 go build ./...` and `make build-rpi` — re-run here, since 3.1 is where the real `go-ldap`/`go-webauthn` import surface first appears and A.5's gate is only meaningful once it does** (A.5 and 3.1 both already mandate this; v10's Verify block omitted it, which is how a mandate goes unrun); `go list -deps ./internal/platform/auth | grep multissh` empty. Commit checkpoint **on the execution branch**.

### Phase D — Mount the gate (O-1)

**4.9 — Wire `cmd/server/main.go`.** Construct once: `provider, svc, limiter, err := auth.FromConfig(cfg.Auth)` — **written in 3.1e**, which is also where the `config.LDAPConfig` → `auth.LDAPConfig` field mapping lives.

**The signature returns FOUR values** — `(Provider, *Service, *LoginLimiter, error)`. *(Corrected in v12; v11 said three here and argued at length that "a two-value form cannot work", while never mentioning the limiter at all — the signature half of CRIT-1/M2.)* A two-value form cannot work because **all nine** guarded handlers moving into the Gate dereference the service (`auth_handlers.go`, the handlers behind `server.go:98-106`), so the Gate needs the `*Service`. A *three*-value form cannot work either, for the same reason one step further: 3.9's `LoginLimiter` is built in this function, is required by `Gate.LoginLimiter`, and had no way out of it. It is the third value. **This call is made exactly once, and the single `limiter` it returns is handed to every `Gate`** (3.1e) — not rebuilt per module.

The resolved protected set comes from **`cfg.ResolvedProtectedModules()`** (B.3b) — the same function `config.Load` validated against, called once here and reused for the registration loop and the fail-closed set below.

Preserve the reference gate exactly, generalized as the **full conjunction**: `NoAuth{}` unless `mode ∈ {"ldap","ldap_passkey"}` **and** the resolved protected set (`protected_modules` plus the `secure_mode` alias) is non-empty; `EnablePasskeys` only for `ldap_passkey`. *(The reference's `!cfg.SecureMode ||` half at `main.go:151` is a conjunction — dropping it would call `EnablePasskeys` for a `ldap_passkey` config with an empty protected set, contradicting B.5's "no module protected → no construction error" invariant.)*

**Every module is wrapped in a `Gate`, protected or not** (3.6b). An unprotected module's Gate carries `NoAuth{}`, serves `GET /api/auth/mode`, and passes everything else straight through. **A module already in round one's 503 state is not wrapped** — the 503 handler replaces the module entirely, including its mode route; a module that failed to build has no auth surface to report on. Gates are installed into round one's existing `built map[string]http.Handler` (built at `cmd/server/main.go:98`, memoized at `:100-109`, with the 503 branch at `:104-106`), so the memoization and the gating share one table.

**Fail-closed on `FromConfig` error, scoped to the protected set.** If `err != nil`, **every module in the resolved protected set is replaced by round one's 503 handler** — never a logged warning, never a fallback to `NoAuth{}`, because the degraded form of an auth gate is no auth gate. Unprotected modules serve normally. This is deliberately **narrower** than making it fatal for the whole binary: round one already rejected that blast radius in its own words — a `known_hosts` typo should not take grocery's shopping list offline — and an unwritable `passkey_store_path` has no more claim on grocery's availability than a bad `known_hosts` does.

**The public-path predicate is per-module, not `/api/`-shaped.** The reference's gate (`middleware.go:46-55`) decides what bypasses auth with:

```go
if strings.HasPrefix(p, "/api/auth/") { return true }
if !strings.HasPrefix(p, "/api/") && (r.Method == GET || r.Method == HEAD) { return true }
return false
```

That second clause reads "a non-`/api/` GET is a static asset". True for multissh, grocery and obsidianoid. **False for menuserver, todo and slideshow** — per A.0b, their data routes are bare paths, so the predicate would serve `GET /items` and `GET /config` unauthenticated on exactly the modules whose data lives there. Promoting a multissh-shaped predicate to a platform address is the one place O-1 is genuinely dangerous.

A single allow-list cannot fix it either: **every module here is a catch-all-at-`/` SPA** with data routes living *inside* that prefix space, so "static bundle minus data routes" is a complement, and a complement is not an allow-list.

**Two prefix lists, private evaluated first:**

```go
// isPublic(r):
//   strings.HasPrefix(p, "/api/auth/")                           -> true
//   matchAny(PrivatePrefixes, p)                                 -> false
//   (r.Method == GET || r.Method == HEAD) && matchAny(Public, p) -> true
//   default                                                      -> false
```

Both lists empty (the zero value) still means **nothing is public** — deny-by-default without a policy type or a compile-time obligation. Registrations, derived from A.0b:

| Module | `PublicPrefixes` | `PrivatePrefixes` |
|---|---|---|
| `multissh`, `grocery`, `obsidianoid` | `["/"]` | `["/api/"]` |
| `menuserver` | `["/"]` | `["/config", "/items", "/menus/", "/api/"]` |
| `todo` | `["/"]` | `["/config", "/items", "/api/"]` |
| `slideshow` | `["/"]` | `["/config", "/items", "/audio/", "/api/", "/" + cfg.Slideshow.Prefix + "/"]` |

The multissh row reproduces `middleware.go:46-55` exactly, including the SPA deep-link fallback (an unknown non-`/api/` GET stays public and reaches `index.html`) — which a single allow-list could not express at all.

**`slideshow`'s private set is computed, not constant** (`handler.go:39` builds the route from `cfg.Prefix`). **Guard the empty case:** `"/" + "" + "/"` is `"//"`, and a `Prefix` of `""` yields `"/"`, marking the entire slideshow SPA private. The default is `"slides"`, and slideshow is not gated in practice, so this is a two-line `if cfg.Slideshow.Prefix != ""` guard, not a validation rule.

**Matching is `strings.HasPrefix`, not path-segment matching** — so a private prefix `/items` also matches `/itemsfoo`. That **fails closed** (it over-matches into private, never under-matches into public) and is therefore accepted as-is rather than tightened; noted here and beside R15 so a reviewer does not read it as an oversight.

*Documented, not enforced.* No `Policy` type, no compile-time obligation. The residual hazard is a **stale `PrivatePrefixes`** after someone adds a data route — that route would be public on a gated module. Accepted and recorded: the lists live next to A.0b's table, adding a route to an existing module is rare, and only multissh is gated in practice. The structural fix (each module exporting its own data prefixes) is a follow-up (§5), deliberately not introduced in a plan going into review.

**Ordering relative to Phase A:** A.2 runs **outside** every Gate, so a cross-origin write is 403'd before any credential is examined.

**Tests — this is the task that catches O-1's new hazard (scenario 1):**

  - **No cookie → the upgrade is rejected** (401 at the gate; the handshake never completes and no SSH session is created).   - **Valid session → the upgrade succeeds**, and **the emitted audit line carries the username** rather than `principal="-"`. **Boot summary (owns §2A observability item (c); new in v11, extended in v12).** At registration, after the loop, emit **one** log line naming **every module in the resolved protected set, the active `auth.mode`, and the login limiter's armed state** — e.g.

```

```

v10's §2A required "auth-gate decisions logged at boot" and **no task emitted it**. Pre-mortem scenario 1 — five modules quietly unprotected — is exactly the failure this line makes visible in one glance, and it is worth more than the WARN in the bullet above because it reports the *resolved* set rather than the configured one, so a `secure_mode` alias that failed to resolve shows up as an absence.

**The `login-limit=` token is new in v12** and implements the Architect/Critic synthesis behind pre-mortem scenario 4: a misconfigured or inert limiter must be visible **every restart**, not only to whoever thinks to grep for a WARN that says nothing is happening. Values: `armed(trusted_cidrs=N)` when a limiter exists and its CIDR list is non-empty; `off` when `auth.mode` is `none` (no login route exists, so there is nothing to limit); and `inert(no_trusted_cidrs)` if the list is somehow empty under a real mode — which B.3's validation should make unreachable, and which therefore deserves to be loud if it ever appears.

**Test:** with a config protecting two modules, the captured boot log names both, names the mode, does **not** name any unprotected module in the protected list, and **contains `login-limit=armed`**.

**4.11 — Thread the audit principal into multissh's audit lines (new; the principal field does not exist).** §2A requires the audit line to name *who* reached which host. **The hard part is scope, not formatting.** **Six** of the `proxy.go` sites (`:140`, `:150`, `:169`, `:181`, `:220`, `:255` — v10 said "seven of the `proxy.go` sites (`:140`–`:255`)"; that range contains six, the seventh `proxy.go` site being the frozen `:315`) sit **inside the WebSocket message pump**, where there is **no `*http.Request` in scope** — the request ended at the upgrade. The principal cannot be read at the point of logging; it has to be captured at upgrade time and carried.

**Mechanism — capture a string, not a dependency.** This is the part that decides whether P1 survives:

- **The `middleware.PrincipalFromRequest` shim is the mechanism — the only one, for both routes.** *(Rewritten in v12, Critic M1. v11 presented "call `auth.PrincipalFromContext` at the upgrade handler in `internal/multissh`'s own HTTP layer" as the **primary** form and the shim as a fallback. **The primary form is impossible for `/api/ssh/ws`:** that route's upgrade handler **is** `package sshproxy` — `internal/multissh/server.go:54` registers `opts.SSHHandler = sshproxy.NewHandler(...)` per `build.go:71` — so the "own HTTP layer" the primary form names does not exist for this route, and following it would force `sshproxy` to import `internal/platform/auth`, which 4.11 forbids two bullets down. v11 therefore specified, as its recommended path, the one thing it also prohibited.)*

  The `Gate` writes the username into the request context under a **`middleware`-owned** string key. Both routes read it through a one-line helper:

  ```go
  // internal/platform/middleware
  func PrincipalFromRequest(r *http.Request) string // "" → "-"
  ```

  - **`/api/ssh/ws`:** `sshproxy.Handler.ServeHTTP` calls `PrincipalFromRequest(r)` **immediately before `upgrader.Upgrade`** and stores the result on the session struct. `sshproxy` imports `internal/platform/middleware` — which it must anyway, for A.1's `OriginChecker` — and **never** `internal/platform/auth`.
  - **`/api/broadcast/ws` and `broadcast.go`'s four sites:** the principal is captured in `handleBroadcastPost`, which **is** in `package multissh`, so there the direct `auth.PrincipalFromContext(r.Context())` call is fine and is what should be used. **Its signature is `(Principal, bool)`** (`reference/multissh/internal/auth/auth.go:85`), not a bare `Principal` — check the bool first and read `.Username` only when true; `"-"` otherwise. It is stored on the **job struct**, which the four call sites already have in scope.
- **Store it on the session struct — NEVER on `ConnectParams`.** *(Emphasized in v12; v11 wrote "the proxy session struct / `ConnectParams`" as though the two were interchangeable. They are not.* `ConnectParams` **is populated from the client's post-upgrade message**, which makes every field on it attacker-controlled. A principal read from `ConnectParams` is a principal the client chose, and the audit line would then faithfully record whoever the attacker said they were — an *anti*-control, strictly worse than the `principal="-"` it replaced.) The principal goes on the **session** struct only: server-controlled, and **set at upgrade time, before any client message is read**.
- **P1 is preserved, and this is the explicit ruling the plan owes:** `internal/multissh/sshproxy` and `internal/multissh/broadcast` **must not import `internal/platform/auth`.** The shim above is what makes that hold for the `sshproxy`-owned route; `package multissh`'s own handlers may name the auth package directly, because that is already the module's boundary with the platform. **A form in which `sshproxy` imports `internal/platform/auth` is not acceptable, and neither is a form that reads the principal from client-supplied data.**
- **Amend the nine call sites** identified above to add ` principal=%q`, appended after `user=` and before `outcome=`. `Auditf` itself is unchanged — it stays a formatting-free passthrough, which is what keeps `TestAuditLinesCarryNoCredential` meaningful.
- The two upgrade-rejection sites (`proxy.go:315`, `broadcast.go:399`) fire **before** any principal is established. They keep their current format **unchanged** — A.1's byte-identical-audit-line requirement applies to exactly these two, so the two tasks do not collide.

**Tests:** with auth off, every amended line carries `principal="-"`; with a session present, it carries the LDAP username; **a client that sends a principal-shaped field in its post-upgrade `ConnectParams` message does not change the logged principal** *(new in v12 — the regression guard for the client-controlled-principal hazard above)*; `TestAuditLinesCarryNoCredential` still passes (a username is an identifier, not a credential — assert it explicitly so the next reader does not relitigate it).

**If this is cut, it must be cut loudly.** 4.11 is the one task here that is a genuine candidate for demotion to a follow-up: it touches nine sites across two files for observability, not for a security control. If demoted, **§2A's Observability row (a) must be deleted, not softened**, §8.6's "round two extends the audit line's principal field" must be struck, and the follow-up recorded in §5 — because a plan that claims principal-attributed audit and does not deliver it is worse than one that never claimed it.

**6.2 — Documentation.** Extend round one's `docs/multissh.md` (and the README auth section) with:
- **LDAPS trust, stated plainly (§0A):** the deployment uses `ldaps://ldap.cmdhome.net`, verified against the **system trust store** with standard `crypto/tls`. No CA file, no pinning, no bootstrap. `insecure_tls` exists for exotic deployments only, disables certificate verification entirely, logs a WARN at startup, and **should not be set in this lab** — if a verified `ldaps://` dial fails, the cause is an untrusted chain, an expired certificate, or a URL naming a host the certificate does not cover — **on the `ldaps://` path it is not a `ServerName` problem**, because `crypto/tls` derives the name from the dial address there (§0A). **Debugging order for `ldaps://`: check the chain, check expiry, check that the URL host matches a SAN — then stop.**
- **The one case where it *is* a `ServerName` problem, and why you will never meet it as a runtime error.** The **StartTLS** path (`ldap://` URL + `start_tls: true`) reaches `crypto/tls` through a different entry point that derives nothing, so with `insecure_tls: false` it cannot complete a handshake at all. **That combination is rejected at config load** with a message naming the limitation (B.3), so it surfaces as a startup error you can read, not as a TLS failure at first login that points you at your certificate. If you hit that error: use an `ldaps://` URL. *(v10 of this plan stated the derivation claim unconditionally and told the operator to stop debugging before reaching this — corrected in v11.)*
- **If login rate limiting is silently not happening, check two things in order: (1) does your nginx vhost set `X-Forwarded-For` at all** (a bare `proxy_pass` does not — see the proxy bullet below, and this is the more likely cause), **and (2) `auth.trusted_proxy_cidrs`** (3.9). The boot summary answers neither on its own — `login-limit=armed` means the limiter was *constructed*, not that the header is arriving — so if it says `armed` and you still see no 429s, the header is the suspect. The limiter keys on the rightmost untrusted `X-Forwarded-For` entry, and only when `RemoteAddr` is itself inside a trusted CIDR. A CIDR list that does not include your nginx means the header is ignored; a request that yields no usable key is **not limited** (and logs a rate-limited WARN) rather than being counted globally — deliberately, because a global counter would let anyone lock the operator out. Grep the log for that WARN if you expect limiting and are not seeing 429s.
- Auth is configured **once at the top level** and applies to whichever modules are listed in `auth.protected_modules`; `multissh.secure_mode: true` is an alias for multissh's membership.
- **Sessions are host-scoped** — the operator logs in once per protected module hostname (§4).
- **The gate denies by default.** Each module declares public static prefixes and private data prefixes; anything not matching a public prefix requires a session. multissh's bundle stays readable before login because multissh **declares `/` public and `/api/` private**, not because non-`/api/` GETs are exempt as a general rule. State it plainly so nobody reads `secure_mode: true` as "nothing is served unauthenticated". No secrets are in the bundle; the host list and key names come from `/api/*`, which is gated.
- **All six modules are now same-origin** — the wildcard CORS header is gone and cross-origin writes to any module are 403'd (A.2/A.3).
- **The proxy must preserve `Host` and must append `X-Forwarded-For`.** **Load-bearing, not advisory — both lines, per vhost:**

  ```nginx
  proxy_set_header Host              $host;
  proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
  ```

  - `Host` is compared against `Origin` by A.2 and by both WS upgraders; `$proxy_host` instead of `$host` **breaks every write on all six modules** (scenario 3).
  - `X-Forwarded-For` is what 3.9's limiter keys on. **A bare `proxy_pass` does not set it at all**, and the limiter's specified behavior when it is absent is to *decline to limit* — so omitting this line leaves login rate limiting silently and permanently inert (scenario 4). Confirm it is armed from the boot summary's `login-limit=armed(...)` token (4.9), not by assuming.
  - **Invariant, stated because the key derivation depends on it: every trusted hop must APPEND to `X-Forwarded-For`, never overwrite or pass it through.** `$proxy_add_x_forwarded_for` appends; `$http_x_forwarded_for` does not. If any trusted hop fails to append, the **rightmost** entry becomes attacker-controlled, and the rightmost-untrusted key derivation — the whole reason the trusted-CIDR design exists — stops protecting against either limiter evasion or targeted operator lockout.
- `ldap_passkey` is supported and requires the fronting proxy to terminate TLS so the browser origin matches `auth.passkey.origins`; the end-to-end authenticator ceremony is untested.
- **Break-glass: what to do when LDAP is unreachable and multissh is gated** (§4). There is no runtime override — B.5 deliberately does not probe LDAP at startup, so an unreachable directory surfaces as a 401 at first login with the binary otherwise healthy. **The recovery is: edit the config to `auth.mode: "none"` (and clear `multissh.secure_mode`, or B.3 will refuse the config) and restart.** State it plainly, with the exact two fields, so the operator is not reverse-engineering B.3's validation rules while locked out. **No config override flag is added** — a "bypass auth" flag is a second, less-tested path to the same outcome as editing two fields the operator already owns on a single-operator LAN box they have shell access to, and it is a permanent fail-open surface in exchange for saving one restart.

## 4. Consequences the operator should know before approving

- **One implementation is not one login.** `setSessionCookie` (`auth_handlers.go:233-243`) sets no `Domain` attribute, so the cookie is **host-scoped**; unified dispatches by Host header, so each module lives on a different hostname. A session established on `multissh.cmdhome.net` is not sent to `grocery.cmdhome.net`. The operator logs in **once per protected module hostname**. Accepted as-is — a single operator, and a domain-wide cookie would need a shared parent domain plus a `Domain=` attribute widening the cookie to every host under it. Recorded so nobody discovers it as a bug later.
- **`protected_modules` is usable for multissh only today** (R14).
- **Sessions do not survive a restart, and expired ones are never reaped.** The ported `sessionStore` is **in-memory only** — there is no persistence and **no background reaper**. Two consequences the operator will meet: **(1) any restart of the binary logs everyone out of every protected module**, so a config reload or a deploy is a forced re-login; **(2) expired sessions are evicted only lazily, on lookup**, so an abandoned session occupies memory until something asks for it again. Neither is a defect at this scale — one operator, a handful of sessions — and both are accepted rather than engineered against. They are recorded because "why did I get logged out?" after a restart is otherwise indistinguishable from a bug.
- **Brute-force protection on the login endpoint is being *added*, not ported** (R17, task **3.9**). The reference has none. Two properties the operator should agree to before approving: **(1) it depends on `auth.trusted_proxy_cidrs` being right.** The limiter keys on `X-Forwarded-For` only when the request arrives from a trusted proxy; if that list is wrong, the limiter **stops limiting** (and logs a WARN) rather than counting every request globally. That fail-**open** is deliberate — the alternative would let anyone on the LAN lock the operator out of his own lab by failing ten logins — and it means a misconfiguration degrades this control silently rather than loudly. **(2) Its state is in memory and clears on restart**, like sessions. **(3) It depends on nginx sending `X-Forwarded-For`** — a bare `proxy_pass` does not, and on such a deployment the limiter is silently inert. 6.2 mandates the header line and 4.9's boot summary reports `login-limit=armed(...)` on every restart so this is visible rather than assumed; the operator should glance at that token after any proxy change. **(4) The 1024-key map cap is a scale limitation, not a clean bound.** Eviction takes the oldest **non-locked-out** entry and refuses to track new keys when all 1024 are locked out, so an existing lockout is never discarded to make room — but an attacker with more than 1024 distinct keys can still fill the table and deny *tracking* to a new honest client. Accepted at this scale for the same reason as the rest of this section — one operator, a LAN, a handful of clients — and recorded honestly rather than presented as solved, because at any larger scale it would not be. All four are acceptable here; all four are recorded so none is discovered as a surprise.
- **Break-glass: there is no runtime auth bypass.** If the directory is unreachable and multissh is gated, the operator gets a 401 at login and the binary is otherwise healthy (B.5 deliberately does not probe LDAP at startup, because the DC may boot slower than the webapp). **The only recovery is to edit the config — set `auth.mode: "none"` and clear `multissh.secure_mode`, both, or B.3 will refuse the file — and restart.** This is a deliberate choice, not an omission: a bypass flag is a permanent fail-open surface, and a less-exercised one, in exchange for saving a restart on a single-operator box the operator has shell access to. 6.2 documents the exact two fields so this is not reverse-engineered while locked out.
- **What the chosen design gives up against Option E″, reconciled rather than left as an unanswered credit.** §1 credits the external-identity-proxy option with brute-force lockout **and** with mature session management, and R17 handles the first. The second is reconciled here: the chosen design's sessions are **in-memory, unreaped, and lost on restart** (bullet above) — precisely the properties a maintained identity proxy would have solved for free. The plan **accepts** that gap rather than closing it, on the same grounds as everything else in this section: one operator, a handful of sessions, a forced re-login on deploy is an annoyance and not a defect. A session reaper and/or a persistent store is the §5 follow-up if it stops being an annoyance. Recorded so that E″'s pro-column is fully answered, the way R17 answered the lockout half.
- **The other five modules change observably**, in three reviewed ways: wildcard ACAO withdrawn and cross-origin writes 403'd (A.2/A.3, the substantial one); a new unauthenticated read-only `GET /api/auth/mode` returning `{"mode":"none"}`; and a login gate **if and only if** listed in `protected_modules`, whose default is empty.
- **Deployment context this plan is calibrated to.** Single-operator home lab on a LAN, behind nginx which terminates TLS, reachable from outside only over Tailscale. Threats are modeled at "a hostile web page the operator visits while on the LAN" (scenario 2 of v8, R9 here), **not** at an internet-facing attacker. Where a constraint can be documented or structurally guaranteed, this plan documents it: no deny-by-default policy types, no compile-time enrollment obligations. *(Note, not a decision: `cmd/server/main.go` binds `0.0.0.0`, not loopback. A `bind_addr` field was considered and demoted to a note — the operator may want `0.0.0.0` for testing and considers the exposure understood.)*

## 5. ADR — Land LDAP/passkey auth as a platform capability and make the binary same-origin

**Decision.** Port `reference/multissh/internal/auth` plus `server/auth_handlers.go`'s handler bodies into a new `internal/platform/auth` package with zero multissh coupling; configure it from a **top-level** `auth` section; apply an `auth.Gate` to **every** module at registration in `cmd/server/main.go`, with a real provider for modules in `auth.protected_modules` (plus `multissh.secure_mode` as an alias) and `NoAuth{}` for the rest; gate paths with per-module public/private prefix lists rather than a multissh-shaped predicate. Independently, move the same-origin policy into `internal/platform/middleware` and apply it to all six modules, closing R9. **Connect to LDAP over `ldaps://` with standard `crypto/tls` verification against the system trust store**, defaulting `insecure_tls` and `start_tls` to `false`.

**Drivers.** (D1) FR-A3/A4/A5 and AC-6 are hard acceptance gates that only a real LDAP login satisfies. (D2) R9 is a live, exploitable defect on a module that executes shell commands, and it is independent of the auth work — so it ships first. (D3) The ported auth stack has zero upstream tests and will front all six modules, so coverage is the acceptance gate, not the port.

**Alternatives considered.**
- *Module-local `internal/multissh/auth`, lift later (Option E′)* — genuinely lower-risk, and five of the six defects the v8 iterations had to fix exist only because auth was generalized before a second consumer existed. Delivers identical operator-visible behavior today. Declined on operator decision O-1 and on "migrate a security-critical package once, not twice". **A sequencing objection, not a destination objection**; recorded in full as §6 and named as the first thing to reconsider under schedule pressure.
- *External identity proxy — Authelia / oauth2-proxy / nginx `auth_request` (Option E″)* — no auth code in this repo, maintained upstream, insertion point already exists. Rejected because FR-A3/A4/A5 specify `/api/auth/*`, `auth.mode`, `required_groups` and `passkey_store_path` as properties of *this* binary, AC-6 gates on that behavior, and a second daemon contradicts the one-binary premise that motivated unified-webapp. The right answer for a product; revisit if the ported stack becomes a maintenance sink.
- *Scope the origin control to multissh (Option F′)* — smaller blast radius for a proxy misconfiguration, and R9's real danger is multissh's alone. Reverses O-3 and puts the load-bearing control where only one module can use it. **Retained as the pre-authorized narrowing if R1 bites.**
- *CSRF tokens instead of an origin check (Option F″)* — immune to `Host` rewriting, so it dissolves R1. Rejected: needs a token endpoint and per-request plumbing in six SPAs, and a session to bind to — which does not exist under `auth.mode: "none"`, the default and the exact configuration R9 is dangerous in.
- *A custom CA pool / cert-pinning config field for LDAPS* — **rejected on the new fact**: the certificate already chains to a system-trusted root, so there is nothing to point such a field at. Adding a knob for a problem that does not exist is how `InsecureTLS = true` became the reference's default. The reference's own `insecure_tls` is retained unchanged as the exotic-deployment escape hatch; no new field is invented.

**Why chosen.** E is the only option that satisfies FR-A3..A5 as written while landing the operator's stated end state directly rather than via port-then-lift, and the C4 defect — the one place O-1 is genuinely dangerous — has a known, expressible fix (the two-list predicate) that this plan specifies rather than gestures at. F is the only option that closes R9 without touching five frontends, and it needs no session, which matters because R9 is worst in the configuration where no session exists. The LDAPS decision is not really a decision: with the certificate trusted, standard verification is both the simplest code and the only defensible posture.

**Consequences.**
- `go.mod` gains LDAP + WebAuthn transitively even though auth defaults to off; binary size grows and the dependency-update surface widens.
- **All six modules become same-origin.** Wildcard ACAO is withdrawn and cross-origin writes are 403'd — the one place this work deliberately diverges from "preserve working behavior" on security grounds, and it applies to five modules the FRD says nothing about. Absent-`Origin` requests stay permitted, so curl and scripted use are unaffected.
- **`Host`-preserving proxy configuration becomes load-bearing for the whole binary** (R1), where today it is load-bearing for nothing.
- **All six modules gain `GET /api/auth/mode`**, unauthenticated and read-only, returning `{"mode":"none"}` on unprotected ones. This is the one thing that changes out of the box for the existing five. **Exception:** a module in the 503 state has no mode route either — the 503 handler replaces the module entirely.
- **`GET /api/auth/mode`'s payload is not byte-identical to the reference** — it gains `maxSessions` (required by FR-N1) and drops `secureOptIn`, a flag derived entirely from `mode` and read by nothing. Verified unreferenced before dropping.
- **Sessions are host-scoped**; the operator logs in once per protected hostname (§4).
- **`protected_modules` is operationally usable for multissh only** until a shared login page lands (R14).
- **LDAP is contacted over verified TLS by default**, and the only way to disable that is a documented flag that logs a warning every time it is used. The end-to-end proof is an env-gated test that binds against the real directory through the production code path (3.8b).
- **LDAP reachability is not validated at startup** — an unreachable directory surfaces as a 401 at first login, not a boot failure.
- **Sessions are in-memory with no reaper**: a restart logs everyone out, and expired sessions are evicted lazily (§4).
- **Login brute-force protection is new code, not ported code** (R17, task 3.9) — the reference stack has none, and the chosen option therefore does not inherit the lockout that Option E″ would have provided for free. It adds one config field (`auth.trusted_proxy_cidrs`) whose only purpose is to make the control work behind nginx, and it fails **open** when that field is wrong. It also makes **two nginx directives load-bearing** — `Host` (shared with A.2) and `X-Forwarded-For` **appended** via `$proxy_add_x_forwarded_for` — and it requires **three lines of change inside the ported `auth_handlers.go`** (3.1's third exception: two recording calls plus reading the context key), which is the plan's only deliberate edit to ported handler logic.
- **`auth.FromConfig` returns four values and errors on an unrecognized mode.** The four-value signature is forced by the limiter having to reach the `Gate`; the mode error is defense-in-depth duplicating B.3's enum check at the point the gate is built, because every auth test constructs the gate directly and bypasses `config.Load`.
- **multissh's `sshproxy` package reads the principal through `middleware.PrincipalFromRequest`, not through the auth package** — forced by `/api/ssh/ws`'s upgrade handler being `package sshproxy` itself. The principal is captured before the upgrade and stored on the server-controlled session struct; it is **never** read from the client-supplied `ConnectParams`.
- **`start_tls: true` with `insecure_tls: false` is not a supported configuration** and is rejected at load (§0A, B.3). This is a real, if narrow, capability reduction against the reference, which would accept the config and then fail every bind. The deployment is `ldaps://`, where `start_tls` is ignored regardless.
- **multissh's audit lines gain a `principal` field** (4.11), which required an explicit ruling that `internal/multissh/sshproxy` carries the principal as a plain string and never imports `internal/platform/auth`.

**Follow-ups (not in this plan).**
- **A session reaper and/or persistent session store**, if forced re-login on every restart becomes annoying (§4).
- **Persist 3.9's rate-limit state**, if a restart-clears-the-counter window ever matters. It does not at one operator on a LAN.
- **`ServerName` on the StartTLS path**, if a `ldap://` + `start_tls` deployment ever appears — two lines setting it from the URL host on the **StartTLS `tls.Config` only**, which lifts B.3's rejection of that combination. It does not contradict the `ldaps://` finding: different `crypto/tls` entry point (§0A).
- **A metrics surface.** §2A item (f)'s per-risk signals are log greps (6.2) because the binary exposes no metrics. If operability ever demands counters rather than `grep -c`, that is a standalone piece of work, not a rider on an auth plan.
- **A shared login page** for the five non-multissh modules, which is what makes `protected_modules` usable beyond multissh (R14).
- **Move each module's data-route prefixes into its own package** (`var DataPrefixes` beside its handler) so 4.9's table stops being a second copy of information that lives in the handlers — the standing fix for R15. Deferred because slideshow's prefix is config-derived and would need a function where the other four are plain vars, and because introducing a mechanism during consensus review is how the v8 iterations generated their defects.
- Complete the WebAuthn end-to-end ceremony once a real authenticator exists (the LDAP half is done, per 3.8b).
- Consider a configurable `allowed_origins` list if a legitimate cross-origin consumer of any module ever appears.
- Domain-scoped session cookies, if the "log in once per hostname" property ever becomes annoying enough to justify widening the cookie.
- Delete `reference/multissh/` once round two has run in production. It is the specification for the auth port and stays **read-only** until then.

## 6. Recorded antithesis — O-1's sequencing

Both reviewers, independently, spent the majority of three v8 iterations' findings on O-1's downstream consequences. That is data about where the complexity sits, and it deserves recording even though the decision stands.

*The argument.* Five of the six defects v6 had to fix exist **only** because auth was generalized to a platform capability before a second consumer existed: the mode route vanishing under the default config; `maxSessions` unable to cross the platform boundary; multissh's URL predicate promoted to a platform address; five modules gateable with no login UI; a silently unprotected module. **None arise under a module-local placement.** O-1 buys a generalization that, per R14, cannot be exercised today, and pays with a new top-level config surface, a shared package between the network and all six modules, R10 raised Med→High, a `map[string]any` whose only job is to smuggle one module's config through a package forbidden to know it exists, and a per-module path policy that took two iterations to reach an expressible shape. The fallback would deliver **identical operator-visible behavior** — multissh gated, five modules untouched — and the lift is *cheaper later*, because by then you extract an interface from two real implementations instead of guessing one from zero.

*Fresh evidence from this iteration — the count is now seven, not five.* Both reviewers of the previous snapshot independently surfaced two **new** defects, and both are the same shape: a **platform↔module boundary problem that does not arise module-locally.**

- **The audit principal (4.11).** The principal has to be captured at the HTTP upgrade boundary — where the auth package lives — and carried into `sshproxy`'s message pump, where it does not. Under a module-local placement, `internal/multissh/auth` and `internal/multissh/sshproxy` are siblings in one module and the value is just a field; the question of whether the package is *allowed* to see the principal never arises. Under O-1 it forced an explicit P1 ruling plus a named fallback shim.
- **The `sameOrigin`/`Auditf` lift (A.1).** The predicate and its audit line are one behavior, but they belong to different layers once the predicate is a platform asset — forcing a choice between inverted layering, a silently dropped audit line, and a logger seam. Module-locally, `sameOrigin` and `Auditf` are in the same package and there is nothing to decide.

Neither is a *design* flaw — both have clean, specified fixes in this plan. Both are **cost** attributable to the generalization, arriving in review round two of round two, which is the antithesis's actual claim: not that O-1 is wrong, but that O-1 keeps generating boundary work that module-local placement does not.

*A sharper statement of the claim, from the Architect's review of v10 — adopted because it is more precise than "generates boundary work".* **O-1 does not merely generate boundary work; it relocates security decisions to places where they cannot be tested cheaply.** That is a stronger and more falsifiable claim, and v10 produced two proofs of it:

- **The gated WebSocket upgrade (4.9, new in v11).** The two highest-consequence routes in the binary went three review iterations with **no test of them under a gate**, because the gate and the upgrade handler now sit on opposite sides of a package seam that only a dispatcher-level test plan can span — and this plan's unit-test layer, which is where the auth coverage lives, cannot reach it. Module-locally, the gate and the upgrader are in the same package and the test is unremarkable.
- **The rate limiter (3.9, new in v11).** It went unowned for a whole iteration because it is **homeless by construction**: it belongs to *the login endpoint*, but it has to live in a package that fronts *six modules* and is forbidden to know which one it is fronting. Nothing about writing a rate limiter is hard; finding the address for it was, and the plan simply failed to, until two reviewers pointed at the same gap.

Both defects are now fixed. The point of recording them is that neither was a *mistake* anyone made — they are the predictable yield of moving the enforcement point away from the thing being enforced, and the yield has now been non-zero in three consecutive iterations.

*The count is four, and the pattern is now specific enough to name.* **v12 is the fourth consecutive iteration in which new content shipped with an unwired mechanism, and both of v11's blocking defects were of exactly that shape:**

- **v11's rate limiter had a read path and no write path.** The check lived in `Gate.Wrap`; the fact it needed — did this login fail? — lived inside a ported handler the plan forbade touching. The counter could never increment. The mitigation was marked "mitigated" in R17 and was inert.
- **v11's `OriginChecker` had one format field and two formats to produce.** The seam was designed against the *layering* problem (who owns the logger) and not against the *behavior* problem (the two sites emit different strings), so its own stated acceptance criterion was unmeetable, and the two tests that existed would both have passed through the regression.

The through-line across all four iterations is the same and it is worth stating plainly rather than absorbing: **this plan is consistently better at deciding *where* a mechanism lives than at verifying that it is *connected at both ends*.** Every one of these defects was found by review, none by the plan's own §6A sweep — which is why v12 extends that sweep's term list with the specific identifiers involved, and why the terms added are *pairs* (`RecordFailure`/`RecordSuccess`, `two exceptions`/`three exceptions`) rather than single words: an unwired mechanism is detectable as a name that appears in one section and in no other.

*Is the E′ retreat trigger firing? — stated explicitly rather than left to drift.* The trigger below reads **"if Phase C exceeds four iterations"**. This is consensus iteration **four**, and Phase C content (3.1, 3.8, 3.9) has been the substance of every one of them. **The honest answer is that the trigger's language is ambiguous and this plan will not resolve that ambiguity silently in its own favor.** Two readings:

- **"Four iterations of *review*"** — then the trigger fires **now**, or fires on the next one.
- **"Four iterations of *implementation attempts* against the seam"** — then it has not fired, because **Phase C has not been executed even once**; every iteration so far has been review of a document.

The second reading is the one the trigger's second clause supports ("*if 3.8 cannot be written against the seam without further production changes beyond 3.1's named exceptions*" — a statement about writing code, not about reviewing a plan). **On that reading the trigger has not fired.** But note the clause's own condition has now *partially* fired: **3.1's named exceptions went from two to three in this revision**, because 3.8's limiter tests could not be written against the seam without one. That is exactly the signal the clause was written to detect, arriving during review rather than during execution — one more such exception and the retreat should be taken seriously rather than argued about. **Recorded as an open question for the reviewers, not decided here:** if the reviewers read the trigger the first way, it has fired, and E′ should be reconsidered before Phase C begins.

*A symmetric, observable trigger for the E′ retreat.* §1's Option F′ already carries one ("if R1 bites, narrow A.2 to multissh"). E′ had none, which made "the first thing to reconsider under schedule pressure" unfalsifiable. It now has one:

> **If Phase C exceeds four iterations, or if 3.8 cannot be written against the seam without further production changes beyond 3.1's three named exceptions (`isPublic`, the clock seam, and 3.9's two recording lines) — retreat to `internal/multissh/auth`.** *(The exception count was two in v11 and is three in v12, having been raised by exactly the pressure this clause measures; see the ambiguity note above for whether the four-iteration half has fired.)* The retreat is cheap by construction: **`Gate`, the two-list predicate, and `FromConfig` all move unchanged, because none of them names multissh.** What changes is the mounting point (`multissh.Build()` instead of `cmd/server/main.go`) and the loss of the five-module reach that R14 says is unusable today anyway. That is the test of whether the generalization is carrying its weight: if the code is genuinely multissh-blind, moving it costs an import path.

*Why the decision stands.* The operator asked for it in plain words ("DRY all the way"), `internal/platform/auth` is where this code ends up regardless, and migrating a security-critical package once beats migrating it twice. The antithesis is about **sequencing, not destination** — which is why it is recorded rather than adopted. If schedule pressure appears, this is the first thing to reconsider, and §1's Option E′ names the fallback as real.

*What was adopted from it.* The two-list gate now expresses every module's contract correctly (4.9), so the generalization is at least **sound** even while only multissh exercises it. Enrolling a second module is a frontend task, not another backend lift.

## 6A. Process note for reviewers
